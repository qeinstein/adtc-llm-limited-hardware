The problem

Community health workers are often the only medical presence for a village.

They are the front line for childhood fever, malaria, pregnancy danger signs and injury. Cloud AI is a non-starter: connectivity is unreliable, subscriptions are priced in dollars, and patient data should not leave the clinic. Whatever helps has to run on the device already in the room.

A health worker needs trustworthy guidance in the language the patient speaks — not a chatbot guessing, and not something that stops working when the signal drops.

The target

We did not build another tiny-model demo.

A 0.5B, 1.5B, or 4B model can be useful for a narrow task. That does not make it a substitute for broader reasoning, language, planning, and clinical context. If Africa keeps treating “small enough to run” as the same thing as frontier intelligence, the capability gap becomes the design.

Fine-tuning can specialise a model. Retrieval can add local facts. Neither changes the base model's underlying capacity. We chose the harder direction: bring a considerably stronger sparse model closer to the hardware African users can actually afford.

12.26 GB on disk → 2.50 GB peak RSS → 16.0 tok/s Official ADTC profiler headline, CPU-only, bounded sparse runtime.

This is a genuine systems breakthrough for the direction, but even this 35B system is still a failure against the real target: it is storage-backed, slower than a server, and not clinically validated. It is nevertheless a meaningful step beyond accepting tiny models as Africa's permanent ceiling.

How it works

Instead of shrinking the model, we shrank its working set.

Jamii Afya keeps a 35-billion-parameter sparse model on a CPU-only laptop by bounding what must be resident in RAM at any moment. Four decisions make that possible.

  1. 35B model, bounded working set

    Qwen3.6-35B-A3B runs with its real router: K4/16 execution, routed experts quantized to Q2_K, and bounded SSD-backed expert staging. Only a small working set is resident at any moment — the capability stays, the RAM bill does not.

  2. A short system prompt

    The model receives one short system prompt: explain the medical reasoning, be honest about uncertainty, and discuss medication only when the user explicitly asks about it.

  3. References when they help

    Offline clinical references are retrieved only when the question has a strong match. Relevant context is placed alongside the question; otherwise the model receives the question directly.

  4. No weight-level fine-tuning

    The weights are untouched. The application assembles the system prompt, optional reference context, conversation history and the user's question, then returns the model's response unchanged.

Development journey

What we tried, what failed, what survived.

The useful parts of a build log are the mistakes. These are the ones that changed the design.

Small models fit. Quality didn't.

We started with sub-billion-parameter small models, because that was the obvious answer to an 8 GB laptop. They were easy to run, but did not meet the capability and safety target we wanted for clinical use.

A larger sparse model changed the question.

Qwen3.6-35B-A3B had far stronger capability, so the problem stopped being model size and became active memory footprint: how little of the model needs to be resident at once.

Naive sparse execution was still too expensive.

Native expert execution and residency still consumed too much memory. K4/16 execution cut the experts computed per token while retaining broader router normalization — that became the execution point.

The profiler caught a real systems bug.

An early profiler run used roughly 15 GB because llama-bench wasn't honoring the bounded lazy-runtime mode. Fixing that runtime path produced the verified 2.50 GB peak / 16.0 tok/s headline.

The model should own the answer.

We removed the intermediate classification, labels, response rewriting and fixed fallbacks. The current path is intentionally inspectable: system prompt, optional RAG context, then model output.
