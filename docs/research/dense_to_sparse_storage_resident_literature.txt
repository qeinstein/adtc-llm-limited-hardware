============================================================
DENSE -> SPARSE -> STORAGE-RESIDENT LLM LITERATURE NOTEBOOK
============================================================

LAST UPDATED: 2026-09-12
CURRENT RESEARCH QUESTION:

Can a large pretrained dense model, with Qwen3.8-27B as the main candidate,
be transformed into a conditionally executed sparse model whose inactive
parameters remain on SSD/flash, while retaining most capability on a
commodity Linux/x86 CPU with less than 8 GB RAM?  The target is single-user
autoregressive decode, eventually using llama.cpp/GGUF, where actual wall
clock tokens/second matters more than FLOP reduction.

RESEARCH SCOPE / EVIDENCE DISCIPLINE:

This notebook deliberately distinguishes:

1. STATIC PRUNING: permanently remove weights.
2. ACTIVATION SPARSITY: many neurons naturally produce zero or small values.
3. CONTEXTUAL SPARSITY: the active parameter subset depends on input context.
4. MIXTURE OF EXPERTS: an explicitly trained router selects parameter groups.
5. MOEFICATION: post-hoc functional partition of a dense FFN.
6. SPARSE UPCYCLING: initialize a new MoE from a dense checkpoint and continue
   training.
7. STORAGE RESIDENCY: inactive weights still exist but are outside RAM.

Numbers are tagged with model, hardware, batch, precision, context/decode
conditions where the source reports them. A FLOP claim is not treated as a
wall-clock claim. “Not reported” is intentional where a source or public
repository does not expose the required measurement.

Evidence status: 22 source records are included below. The source set contains
papers, implementation repositories, primary model/configuration files, and a
storage-energy analysis. Edge0, DejaVu and PowerInfer code were inspected from
the repositories; Edge0 was inspected at commit 03a5a15, DejaVu at ee902c1.
The notebook is a research artifact, not an implementation plan approval.

------------------------------------------------------------
1. EXECUTIVE SYNTHESIS
------------------------------------------------------------

CURRENT STATE OF THE EVIDENCE

Prior art establishes each major ingredient separately, and recent work has
now combined most of them:

- MoEfication shows that a dense FFN can be partitioned into functionally
  aligned neuron experts and selected at runtime without changing the total
  dense parameter count. It is primarily a ReLU-era method and does not by
  itself solve modern gated FFNs or SSD I/O.
- DejaVu shows that an already dense model has contextual head and MLP
  sparsity and that shallow predictors can choose sparse structures before
  the expensive operation. It reports GPU wall-clock speedups, not an SSD
  resident CPU design.
- LLM in a Flash, PowerInfer and PowerInfer-2 show that storage bandwidth,
  read granularity, neuron bundling, hot/cold placement, caches and overlap
  can matter more than nominal arithmetic. Their device and activation
  assumptions differ from Linux/x86 NVMe.
- Edge0 demonstrates a practical SSD-resident sparse-MoE runtime with
  mmap-backed expert bundles, global LRU, prefetch buffers, fixed staging
  slots, asynchronous cross-token/cross-layer routing prediction and
  adapter recovery. It starts from a sparse MoE checkpoint; it does not
  demonstrate dense Qwen3.8 -> sparse conversion.
- DynaMoE demonstrates post-training conversion of dense MLPs into nested
  variable-width experts with a router and modest continued fine-tuning. It
  has no real storage-resident benchmark and its quality drops are material
  at aggressive budgets.
- NeuroPrefetcher is the closest recent system analogue: it predicts future
  sparse masks, stores neuron records in a storage-friendly layout, reads
  only mask deltas, reuses fixed slots, and overlaps NVMe with execution.
  Its evaluation is Jetson GPU/Arm/unified-memory, not x86 CPU, and it still
  achieves only roughly 1.7-3.7 tok/s under 9-13.2 GiB caps on its reported
  workload. This substantially narrows any claim that delta prefetching or
  neuron-centric SSD layout is new by itself.
- A late implementation audit found direct llama.cpp prior art: Swap-MoE
  provides a CPU-only mmap/demand-paging patch with LRU, fixation and previous-
  pass prefetch; a llama.cpp RFC reports compact expert slot pools with
  `pread`; FlashMoE learns cache eviction; and HOBBIT combines mixed precision,
  prefetch and cache policies. These systems make a Qwen-specific sparse
  conversion and x86/GGUF measurement more clearly the remaining gap.

WHAT PRIOR ART ALREADY ESTABLISHES

- A bounded resident working set plus a larger storage-resident model is
  physically possible. The hardest issue is the bytes and latency of the
  changing working set, not mmap syntax.
- SSD reads need large, coalesced, reuse-heavy transfers. Small random reads
  can erase the benefit of sparsity. A practical design must store aligned
  gate/up/down neuron or group records and maintain fixed staging slots.
- Prediction must happen early enough to hide storage. A predictor launched
  immediately before an FFN is usually too late if that FFN has to be read
  from SSD. Cross-layer or cross-token prediction is the useful pattern.
- A gated FFN must preserve the shared intermediate index: the same neuron
  row in gate and up and the corresponding column in down. Loading one
  projection without the aligned others is incorrect.
- The storage system needs a cache policy, explicit prefetch queue, bounded
  staging buffers, a miss/fallback policy and statistics. mmap alone is not a
  storage scheduler.
- A dense model can expose substantial contextual sparsity, but modern SiLU/
  SwiGLU is less naturally sparse than ReLU. A paper reporting 90% ReLU
  sparsity is not evidence for 90% safe Qwen3.8 SwiGLU sparsity.
- Reducing active FFN work does not make all model compute disappear. Qwen3.8
  has 48 linear-attention/hybrid blocks, 16 full-attention blocks, embedding,
  normalization and output-head costs that remain unless separately changed.

WHAT REMAINS UNSOLVED FOR THIS TARGET

- No source found demonstrates a dense Qwen3.8-27B checkpoint transformed into
  a gated, group-sparse, SSD-resident model on a Linux/x86 commodity CPU,
  inside 8 GB RAM, with 10-20 single-stream decode tok/s and measured quality
  retention.
- There is no reliable public estimate of the safe active-neuron fraction for
  the exact Qwen3.8-27B gated DeltaNet/full-attention hybrid. This must be
  measured, not borrowed from OPT, ReLU, sparse Qwen2, or native MoE models.
- The CPU cost of gathering/repacking quantized Qwen rows, dequantizing small
  groups, applying the gate/up product, and writing a down projection is not
  established. Sparse matmul overhead can dominate after the arithmetic is
  reduced.
- A predictor must be judged against storage bytes/token, false negatives and
  cache misses, not only mask accuracy. A false negative may require an
  emergency read or cause a quality error; a false positive wastes SSD and
  bandwidth.
- Under 8 GB, a dense resident prefix, embeddings/output head, attention/
  linear blocks, predictors, KV cache and staging/cache memory may leave too
  little room for useful active MLP rows. Exact accounting is needed.

STRONGEST EVIDENCE THE IDEA CAN WORK

- Edge0 reports 2.9 GiB peak active memory for an SSD-offloaded 35B-class
  sparse model and 14.9-17.7 tok/s decode on an M4 Pro, with 4-bit expert
  bundles and prerouting. This validates the systems pattern, although not
  the target model, CPU or conversion method.
- LLM in a Flash reports 669 ms/token-equivalent end-to-end latency for OPT
  6.7B on M1 CPU using selective persistence, prediction, windows and
  bundling, versus 3182 ms for a naive baseline in its single-stream setup.
- DejaVu reports 1.8-2x over FasterTransformer on 8 A100 GPUs at structured
  sparsity, with no measured accuracy loss for its tested OPT workloads.
- PowerInfer-2 reports a 47B Mixtral-family model at 11.68 tok/s on a phone
  at a high memory budget, and 2.13 tok/s at a 7 GB memory budget. Its
  cluster/cache/pipeline ablations show that cache hit rate and overlap, not
  arithmetic alone, produce the gain.
- NeuroPrefetcher reports 82-85% token-to-token active-neuron persistence and
  103 MiB/token NVMe reads at a 14.8 GiB cap in its Jetson setup. Delta
  reads and fixed slots are therefore credible design tools, even though
  the absolute throughput target is not yet met.

STRONGEST EVIDENCE IT MAY FAIL

- A 4 GB/s effective SSD budget provides only 400 MB/token at 10 tok/s, or
  200 MB/token at 20 tok/s, before other I/O, queueing, filesystem and
  overlap losses. At realistic random-read rates the budget can be far lower.
- Qwen3.8 has approximately 17.1B MLP parameters. At 4-bit storage the MLP
  pool is roughly 9.6 GB including a rough group-scale overhead, so even 10%
  fresh reads can be about 1 GB per token if reuse is poor.
- Modern SiLU/SwiGLU does not zero the up branch, and it generally has less
  exact activation sparsity than ReLU. Thresholding small contributions can
  change the output continuously rather than merely skipping exact zeros.
- For an 8 GB machine, the non-MLP model, output head, KV cache, runtime,
  predictor and staging buffers may consume most of RAM. If the resident
  floor is 5-7 GB, the active SSD working set becomes very small.
- Published sparse systems mostly use GPUs, NPUs, Apple unified memory or
  native sparse MoE checkpoints. Their kernels and memory systems do not
  prove a CPU/GGUF design.
- SSD offload can be energy-expensive: one 2025 analysis estimates up to
  roughly 12x the per-token energy of HBM for SSD-resident MoE weights. This
  is not a throughput kill by itself, but it matters for sustained deployment
  and flash endurance.

LIKELY ARCHITECTURE

The most plausible path is a hybrid, not a pure new MoE:

1. Keep embeddings, output head, all norms, routers/predictors, linear
   attention and full-attention projections resident where possible.
2. Treat the three Qwen3.8 MLP matrices as aligned intermediate-neuron
   records. Build groups large enough for sequential/coalesced SSD access,
   probably 128-512 intermediate neurons rather than single neurons.
3. Use a dense calibration trace to rank the actual gated contribution
   `|silu(gate_i) * up_i|^2 * ||down_i||^2`, and measure group-level error and
   token-to-token persistence.
4. Start with a training-free or lightly trained lookahead predictor. A
   low-rank/SVD gate predictor is attractive for a no-large-training path;
   a DejaVu/DynaMoE-style learned predictor may recover more quality.
5. Store group records in a GGUF-compatible or adjacent file with aligned,
   coalesced gate/up/down data. Maintain fixed staging slots and read only
   predicted-set deltas. Keep a resident hot core and use a bounded LRU for
   cold groups.
6. Add distillation/fine-tuning only after exact activation traces establish
   a viable sparsity/bytes envelope. Do not begin by building a full MoE
   router and assuming it will preserve the dense function.

LIKELY BOTTLENECK

The limiting resource is the maximum number of fresh, non-reused quantized
bytes that must be delivered per decoded token, multiplied by the latency and
CPU overhead of small/random reads and sparse kernels. The main mathematical
compute may become secondary. A second likely bottleneck is the resident
floor: Qwen3.8's attention/linear/hybrid path and output head may leave no
useful RAM for a large dynamic MLP cache under 8 GB.

POSSIBLE NOVELTY

The core ideas—contextual sparsity, neuron grouping, prediction, SSD
streaming, delta prefetch, hot/cold caches and fixed staging—are already in
the literature. The plausible contribution is an empirically validated
combination for a dense Qwen3.8-style gated hybrid model on Linux/x86,
including a post-hoc conversion, CPU/GGUF-oriented quantized layout, exact
bytes/token and quality/latency tradeoffs under an 8 GB cap. This is a
combination claim only; novelty must not be claimed until a more exhaustive
search and a direct comparison are completed.

[S01] EDGE0

TITLE: Edge0: Streaming Mixture-of-Experts Inference at the Edge
AUTHORS: Edge0-AI repository authors
YEAR: 2025 repository snapshot inspected; README does not establish a peer-
      reviewed publication year
VENUE: Open-source implementation
URL: https://github.com/Edge0-AI/Edge0
CODE: Repository, commit 03a5a15; docs/architecture.md,
      docs/streaming.md, docs/prerouter.md, streaming/{mmap,cache,layer}.py,
      engine/{hooks,qwen}.py, prerouter/{heads,install}.py
RELEVANCE: high

PROBLEM:
Run sparse MoE models whose expert weights exceed practical DRAM without
loading the whole expert pool, while preserving useful decode throughput.

KEY IDEA:
Keep the non-expert model resident, mmap quantized expert bundles from SSD,
reuse a global bounded cache, stage predicted experts into fixed slots, and
overlap prefetch with model execution. Recover some quantization/sparsity
quality loss with LoRA adapters. A learned prerouter predicts the next layer
and next token's expert set before it is needed.

ARCHITECTURE:
The public configurations are Qwen3.5-MoE 35B-A3B (40 layers, 256 routed
experts, top-4 plus one shared expert) and Ling 3.0 8B (24 layers, 128
experts, top-8). The README describes 4-bit weights, approximately 23 GB
and 4.2 GB disk footprints, and claimed peak active memory of about 2.9 GB
and 1.0 GB respectively. The backend in the inspected repository is MLX on
Apple Silicon, not Linux/x86 CUDA or llama.cpp.

ALGORITHM:
Each expert bundle contains gate/up/down weight, scale and bias ranges. The
Qwen gated computation is `down(silu(gate(x)) * up(x))`. The bundle order is
important: fused gate/up has gate rows followed by up rows; using the wrong
order produces a large numerical error.

The mmap reader opens each safetensors shard with `mmap.ACCESS_READ`, parses
the header and returns zero-copy byte slices. `madvise(MADV_WILLNEED)` and a
sequential walk are available, but the public code does not use MAP_POPULATE
and does not guarantee residency.

`SharedExpertCache` is a global OrderedDict LRU keyed by `(layer, expert)`;
this is not one full cache per layer. `PrefetchBuffer` is a separate,
capacity-bounded OrderedDict. A request searches pinned/hot data, shared LRU,
prefetch entries and in-flight futures before building a bundle from its nine
quantized ranges. Thread pools perform load and prefetch work.

The staged path maintains fixed tensor slots and an expert-to-slot table.
Survivor experts remain in their slots, changed experts overwrite slots, and
an overflow slot can represent a missing expert as zero/drop. GPU-side slot
selection avoids host synchronization. `staged_sync` is needed when the
actual used set is reconciled; `staged_replace` can use predicted indices as
the execution set and the production prerouter mapping is intended to avoid
drops.

The prerouter is cross-token and cross-layer. A head owned by layer N reads
that layer's MoE input and predicts layer N+1. Layer N+1 consumes the
prediction made at token t-1, producing one-layer/one-token lookahead. Its
input concatenates the hidden state and current/previous top-k one-hot route
features. A two-layer head is used, with hidden width 512, fp16 by default.
The implementation falls back to the true router for initial/uncovered
layers/tokens.

IMPORTANT EQUATIONS:
Gated MLP:
`y = down(silu(gate(x)) * up(x))`.

Quantized affine group of 64 (conceptually):
`w ~= scale * q + bias`, with packed 4-bit values. The inspected layout
stores weight u32 arrays shaped `[experts, output, input/8]` and bf16
scales/biases shaped `[experts, output, input/64]`.

The staged execution is effectively:
`slot = expert_to_slot[layer, expert_id]`
`selected_bundle = staged_tensor[layer, slot]`.
Missing slots can be zero, exact-loaded, or dropped depending on mode.

TRAINING REQUIRED:
The streaming runtime itself does not require training. Edge0's Recover-LoRA
adapters require a recovery/fine-tuning procedure. The prerouter is trained
or supplied with checkpoint heads. The public documentation does not give a
complete predictor training dataset/optimization recipe or a full accuracy
breakdown for the predictor alone.

INFERENCE MECHANISM:
Prefill can use a full-layer path: direct stacked tensor load avoids building
256 individual expert bundles. Decode uses exact per-expert, hot-cache, or
staged fixed-slot paths. Hooks prefetch previous-token expert sets and stage
the prior layer's used set. The Qwen engine stages and swaps the next set at
each non-full forward. Hot pinning uses decayed counts plus predicted-expert
bonus; hot data can be materialized for a layer window.

MEMORY BEHAVIOR:
The expert weights remain mmapped/SSD backed and are not all loaded up front.
The global cache has fixed capacity; staging and prefetch buffers are bounded.
Embeddings, attention/linear layers, routers, norms, shared experts, output
head and runtime state remain resident. Peak active memory in README examples
is 2.9 GiB for edge0-35b and 1.0 GiB for edge0-8b, excluding the full mapped
expert address space and adding KV cache for long context.

I/O BEHAVIOR:
Each expert miss causes several byte-range reads. Prefetch submits futures;
the callback inserts completed bundles in the prefetch cache and tracks
wasted prefetch. The system can reuse a global cache across layers. Staged
slots trade exactness for predictable indexing. Public docs/code expose load,
hit, prefetch and wasted-prefetch counters, but the inspected README/docs do
not publish a complete bytes-moved/token or cache-hit table.

THROUGHPUT RESULTS:
README benchmark: Apple M4 Pro, 3.3k prompt tokens, 10 warmup, 200 decode
tokens, two runs. Edge0-35b reports 14.9-17.7 tok/s and 2.9 GiB peak active
memory; edge0-8b reports 23.9-25.3 tok/s and 1.0 GiB. Prerouter is claimed
to improve decode throughput by up to 59%. Prefill cold/warm values are
reported as approximately 113/140 and 500/1428 tok/s for the two examples.
These are Apple/MLX results, not CPU/x86 measurements.

QUALITY RESULTS:
README average score is 79.2 for edge0-35b int4 plus adapters versus 83.2
for its fp16 base, and 69.9 versus 72.7 for edge0-8b. This includes the
sparse/quantized checkpoint and recovery adapters; it does not isolate SSD
miss errors or prerouter errors.

HARDWARE:
Apple M4 Pro, MLX, Apple Silicon. No Linux/x86 path is present in the
inspected repository; CUDA is listed as a future direction.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Resident non-expert computation, 4-bit weights, bounded global reuse,
coalesced expert bundle reads, fixed staged GPU lookup, asynchronous load,
and cross-layer/cross-token prediction. FLOP reduction alone is not enough.

WHAT DID NOT WORK:
The repository supports several fallback paths because staging can miss,
prefetch can be wasted, and exact/hot/full-layer execution are needed for
different phases. Staged execution can represent missing experts as zeros or
must fall back to exact loads. The design is not a general x86 implementation.

LIMITATIONS:
The base model is already sparse MoE, so Edge0 does not answer how to derive
experts from dense Qwen3.8 weights. It does not publish the desired bytes per
token, cache-hit distribution, SSD random-read breakdown, or an 8 GB x86
result. Mmap is a virtual-memory interface, not proof that SSD latency is
hidden. The hybrid model also leaves a resident compute floor.

ASSUMPTIONS:
Expert tensors can be independently ranged from shards; predicted experts are
available early enough; a global cache is better than isolated per-layer
caches; MLX asynchronous execution is safe with the chosen synchronization;
4-bit quantization and LoRA can recover acceptable quality.

TRANSFER TO QWEN3.8-27B:
Copy the expert/neuron bundle layout, global LRU, fixed slots, prefetch queue,
hot pinning, full-layer prefill path, counters and one-layer/one-token
lookahead. Replace native MoE experts with aligned gated-FFN groups and build
a Qwen3.8-specific CPU implementation. Do not assume Edge0's 256-expert
route distribution, quality, Apple latency or bytes/token.

TRANSFER TO LLAMA.CPP:
The conceptual cache/staging/prefetch design transfers. MLX tensors,
`gather_qmm`, Python thread callbacks and Apple execution do not. llama.cpp
will need explicit GGUF tensor records, an x86 sparse/gather kernel and a
storage-aware scheduler that avoids implicit page faults.

WHAT WE SHOULD COPY:
[PRIOR ART] One global cache; separate prefetch buffer; fixed staging slots;
slot-table routing; explicit actual-vs-predicted statistics; full-layer
prefill; hot pinning; early cross-layer/cross-token prediction; exact fallback.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Treating mmap as the entire I/O design; relying on zero/drop
misses without a measured quality guard; assuming Apple/MLX asynchronous
behavior transfers to x86; building one tiny request per neuron; claiming
bytes/token without counters.

OPEN QUESTIONS:
Can Qwen3.8 gated neuron groups achieve enough overlap and reuse at 8 GB?
What fixed group size gives the best CPU/SSD tradeoff? Can a predictor's
false negatives be repaired without synchronous random reads? How should
quantized down columns be repacked?

[S02] MOEFICATION

TITLE: MoEfication: Transformer Feed-forward Layers are Mixtures of Experts
AUTHORS: Zhang et al.
YEAR: 2022
VENUE: Findings of ACL 2022
URL: https://arxiv.org/abs/2110.01786 ; https://aclanthology.org/2022.findings-acl.71/
CODE: https://github.com/thunlp/MoEfication
RELEVANCE: high

PROBLEM:
Exploit the observation that only a small fraction of dense FFN neurons are
strongly active for an input, without initially training an MoE architecture.

KEY IDEA:
Partition an existing FFN's intermediate neurons into experts. Every expert
keeps the corresponding columns of W1/b1 and rows of W2, so selecting a subset
is functionally meaningful. Predict which experts matter for each input and
run only those experts.

ARCHITECTURE:
For a simple ReLU FFN, `h = x W1 + b1`, `F(x)=sigma(h) W2+b2`. Partition
intermediate width `d_ff` into k experts of width `d_ff/k`, after permuting
W1 columns and W2 rows consistently. Selecting all experts is the original
dense FFN; selecting a subset reduces the intermediate work.

ALGORITHM:
The paper constructs experts by neuron coactivation. One stated similarity
is the positive coactivation graph weight
`C(n,m) = sum_x h_n h_m 1(h_n>0 and h_m>0)`, followed by graph partitioning
(METIS). The released fast path also has a FAISS K-means/balanced assignment
implementation. It normalizes W1 neuron vectors, creates expert centers,
and uses center similarity to score groups. A small MLP predicts expert
scores from x; top 20% is selected in the main experiments.

In the code, `MLPCenter` is two linear layers without bias with tanh between;
the first layer is initialized from centers and the second approximately
identity-like. The training script uses BCE against normalized positive
activation-score labels, Adam at lr .01 for 30 epochs. It is a calibration/
predictor training procedure, not dense-model pretraining.

IMPORTANT EQUATIONS:
For expert e with neuron set I_e:
`F_e(x) = sigma(x W1[:,I_e] + b1[I_e]) W2[I_e,:]`.
The full output is the sum over all experts for linear output accumulation.

The similarity predictor cost is reported as approximately `O(k d_model)`;
with expert width 32 this can be `O(d_model^2/8)`, plus the small MLP cost.

TRAINING REQUIRED:
Activation traces/calibration data and router training are required. The
paper relu-fies BERT for its GELU experiment and reports roughly 400 update
steps to adapt versus about 10k pretraining steps, but that does not prove a
safe Qwen3.8 SiLU conversion. It is not training-free.

INFERENCE MECHANISM:
Compute/predict expert scores, choose top-k groups, run their submatrices and
accumulate. Ground-truth selection is an upper bound; a classifier produces
the deployable route.

MEMORY BEHAVIOR:
Total parameter count is approximately unchanged by partitioning. The groups
can be laid out independently, which is the useful bridge to SSD residency.
The paper does not implement SSD paging or a bounded RAM cache.

I/O BEHAVIOR:
Not measured. Grouping creates a potential storage unit, but the paper's
experiments assume weights are already available.

THROUGHPUT RESULTS:
At 50%, 25% and 12.5% selected, reported speed ratios are approximately
1.50/1.43/1.15, 2.00/1.98/1.20 and 2.40/2.28/1.47 for theoretical FLOPs/
CPU/GPU respectively. The CPU/GPU experiments use batch/sequence settings
around 64, Intel Broadwell and Tesla V100; they are not single-token decode.
Attention becomes a bottleneck. The CPU numbers are more relevant than FLOPs
but still do not establish Qwen3.8/x86/SSD behavior.

QUALITY RESULTS:
At 20% selection for T5-Large, original SST2/MNLI/RACE scores are about
96.2/89.5/81.3; coactivation plus MLP is about 95.4/87.5/79.0, while
ground-truth selection is about 96.3/89.1/80.8. Calibration reduces an
average drop reported near 1.5 points to near 0.3 points in the tested cases.
T5-XL examples retain roughly 98% quality at 10% selected for easier tasks;
RACE is harder. Usage has a long tail: general experts can serve over 80%
of examples while input-specific experts serve under 10%.

HARDWARE:
Intel Broadwell CPU and Tesla V100 GPU; older transformer models/T5/BERT.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Aligned neuron partitioning plus structured submatrix computation; not disk
offload. CPU wall time follows arithmetic better than GPU, but attention and
router overhead limit end-to-end gains.

WHAT DID NOT WORK:
Naive/ground-truth interpretation is not a deployable router; classifier
errors reduce quality. ReLU assumptions and expert granularity are important.
The method does not solve small SSD reads, gated activations or continuous
nonzero SiLU outputs.

LIMITATIONS:
The most important limitation for Qwen is the activation. A simple ReLU
positive/nonpositive mask does not exist for `silu(gate) * up`; up values can
be negative and SiLU is not exactly zero on negative inputs. Old experiment
percentages cannot be transferred. The reported wall-clock experiments use
larger batches/sequence processing than our single-token target.

ASSUMPTIONS:
Neurons are separable into groups; selected groups preserve enough function;
the router can be evaluated cheaply; submatrices can be computed efficiently.

TRANSFER TO QWEN3.8-27B:
Partition the intermediate index jointly across gate, up and down. For group
I, load gate rows I, up rows I and down columns I. Use contribution-aware
scores, not just positive gate counts:
`q_i(x)=|silu(gate_i(x))*up_i(x)|^2 * ||down[:,i]||^2`.
Group scores should include within-group interference/correlation. A first
calibration can use exact full FFN outputs and measure grouped truncation.

TRANSFER TO LLAMA.CPP:
The grouping/reordering idea transfers. A GGUF converter must repack aligned
groups and a kernel must gather contiguous group rows/columns. Generic dense
GGML matmul does not automatically obtain the benefit.

WHAT WE SHOULD COPY:
[PRIOR ART] Function-preserving neuron permutation, aligned W1/W2 grouping,
calibration labels, a small score predictor, and comparison against
ground-truth group selection.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] ReLU positivity labels, “10% active” claims for Qwen,
unstructured tiny groups, or CPU speed ratios measured at batch 64.

OPEN QUESTIONS:
What group size balances contribution error with SSD sequentiality? Does
coactivation computed on gated contributions remain stable over long decode?
Can a group predictor be trained from only a small calibration set without
false negatives that force synchronous reads?

[S03] LLM IN A FLASH

TITLE: LLM in a flash: Efficient Large Language Model Inference with Limited Memory
AUTHORS: Alizadeh et al.
YEAR: 2024
VENUE: ACL 2024
URL: https://arxiv.org/abs/2312.11514 ; https://aclanthology.org/2024.acl-long.678/
CODE: No primary runtime repository identified in the paper record.
RELEVANCE: high

PROBLEM:
Run LLMs when model weights exceed DRAM by using flash storage without turning
every token into a catastrophic random-I/O workload.

KEY IDEA:
Persist embeddings and attention in DRAM, predict only the useful FFN
neurons, read them in windows, reuse recent neurons, and bundle corresponding
up/down data so flash transfers are larger and more sequential.

ARCHITECTURE:
The selective-persistence design keeps approximately one third of the model
(embedding plus attention) resident and treats active FFN rows/columns as a
working set. The paper uses ReLU/FATReLU-like sparsity and low-rank predictors.

ALGORITHM:
A predictor uses an attention output to estimate positive up-projection
neurons before loading them. The predictor is trained on 10k C4 samples for
two epochs and deliberately overpredicts by about 3x. Reported OPT false
negative and false positive rates are approximately 5% and 7% in one setup,
with later layers more sensitive. A low-rank predictor is used to reduce
overhead.

Windowing with k=4 or 5 reuses recently active sets. The incremental read is
conceptually `S_agg(k+1) - S_agg(k)` instead of reloading the entire current
set. Row-column bundling stores the ith up column with the ith down row. The
paper notes that naive hot-neuron bundling can be negative when a row/column
has high degree, so coactivation and layout must be measured.

IMPORTANT EQUATIONS:
For a token, a useful first-order latency decomposition is:
`T_token = T_I/O + T_memory_management + T_compute`.

Flash has higher first-byte latency for small/random access, but large reads
(reported around 32 KiB or more) can be serviced with many threads. On an M1
Max, the paper reports approximately 6.1 GiB/s for dense sequential reads and
1.25 GiB/s for sparse/random access in a relevant configuration.

The target storage traffic is the selected weight volume. For this project:
`B_effective_per_token = bandwidth / tokens_per_second`.
Thus 4 GB/s / 10 tok/s = 400 MB/token and 4 GB/s / 20 tok/s = 200 MB/token
as absolute upper bounds; filesystem, queue, CPU and overlap reduce them.

TRAINING REQUIRED:
Predictor training and calibration. The base model is not converted to MoE.

INFERENCE MECHANISM:
Predict, issue grouped reads, allocate fixed DRAM rows, copy active up/down
pieces, and reuse a sliding window. The implementation uses many read threads
and bypasses OS cache in throughput measurements to make I/O explicit.

MEMORY BEHAVIOR:
Approximately half of the model is placed outside DRAM in the headline
experiments; embeddings/attention remain resident. Preallocated rows avoid
fragmentation and swap overhead. This is a bounded working-set strategy, not
a proof that an arbitrary 27B model fits below 8 GB.

I/O BEHAVIOR:
Naive random sparse reads are slow. A reported OPT 6.7B, 16-bit example gives
approximately 6.10 GB/s and 2196 ms for naive I/O, 1.09 GB/s and 738 ms with
the predictor, then about 0.2 GB and 164 ms with windowing, and about 0.2 GB,
2.25 GB/s and 87 ms with bundling in one comparison table. These table values
are component measurements, not a universal per-token law.

THROUGHPUT RESULTS:
Single sequence, approximately 128 prompt + 256 generation tokens. OPT 6.7B
end-to-end times are reported as about 669 ms for the proposed CPU path versus
3182 ms for the naive baseline on M1; M1/M2/GPU variants are also reported.
Falcon, Persimmon and Phi2 examples are approximately 706, 1041 and 546 ms
in the table. Hardware is Apple M1/M2 and GPU variants, not x86 NVMe.

QUALITY RESULTS:
For Llama2 in the sparse setup, MMLU is reported around 41.8 dense,
38.96 sparse and 38.63 predictor. This is a real quality cost, not merely a
FLOP result. The paper also evaluates perplexity and model-specific tasks.

HARDWARE:
Apple M1 Max/M1/M2 and associated GPU/Metal/PyTorch/MLX-style systems. Single
sequence; not llama.cpp and not commodity Linux CPU.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Selective persistence, overprediction to reduce false negatives, temporal
window reuse, large row/column transfers and preallocated buffers. The key
lesson is layout plus reuse, not mmap by itself.

WHAT DID NOT WORK:
Naive paging/random reads; small read granularity; predictor false negatives;
bundling without coactivation analysis. Memory management is a first-class
term in the cost model.

LIMITATIONS:
ReLU/FATReLU assumptions, Apple storage/memory stack, no Qwen3.8 gated FFN,
no x86 CPU results, and roughly half-model DRAM rather than an 8 GB absolute
cap. The reported speedups do not directly imply 10-20 tok/s for a 27B model.

ASSUMPTIONS:
Active neurons can be predicted from current context; recent active sets are
reusable; flash large reads are much more efficient than tiny reads; attention
and embeddings fit in resident memory.

TRANSFER TO QWEN3.8-27B:
Copy the cost model, resident-vs-streamed partition, sliding-window reuse,
coactivation-based bundling and fixed rows. Replace positive ReLU neuron
selection with contribution-aware gated-group selection and measure whether
Qwen token-to-token overlap is high enough.

TRANSFER TO LLAMA.CPP:
Copy the explicit storage scheduler and packed layout. Avoid relying on
generic page faults. A C++ implementation should expose reads/token,
read-size histogram, queue depth, cache hits, overlap and stall time.

WHAT WE SHOULD COPY:
[PRIOR ART] Window reuse; up/down row-column bundles; resident attention
floor; overprediction policy; preallocated staging; bandwidth-first accounting.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] ReLU sparsity rates or Apple timings as Qwen/x86 estimates;
uncounted random I/O; and a predictor trained only on prompt contexts if its
distribution shifts during generation.

OPEN QUESTIONS:
What is the equivalent of FATReLU for unmodified Qwen SwiGLU? Is a group
large enough for SSD reads still accurate? Does Qwen's hybrid linear attention
produce stronger or weaker active-set reuse than OPT?

[S04] POWERINFER-2

TITLE: PowerInfer-2: Fast Large Language Model Inference on a Smartphone
AUTHORS: PowerInfer-2 authors
YEAR: 2024
VENUE: arXiv preprint
URL: https://arxiv.org/abs/2406.06282 ; https://arxiv.org/pdf/2406.06282
CODE: https://github.com/SJTU-IPADS/PowerInfer ; https://powerinfer.ai/v2/
RELEVANCE: high

PROBLEM:
Run models larger than smartphone memory by making neuron activation and
storage/compute scheduling aware of heterogeneous NPU, CPU and UFS behavior.

KEY IDEA:
Use neuron clusters as the unit of activation/I/O, keep frequently used hot
clusters in a segmented cache, stream cold clusters through a pipelined gate/
up/down execution path, and place work on NPU or CPU according to locality.

ARCHITECTURE:
For a typical 14336 x 4096 FFN, a 50% offload example uses 7168 hot neurons
and 7168 cold neurons. CPU cold chunks are around 512 x 4096. Cluster sizes
adapt to activation similarity. Decode uses NPU dense hot clusters and CPU
sparse cold work; prefill can use dense NPU processing.

ALGORITHM:
Clusters with similar activation are created offline. Gate/up/down for a
neuron are bundled. After removing hot neurons, the paper reports about 80%
coactivation for corresponding Gate+Up+Down. It can read the gate first and
skip up/down for a zero gate, saving around 20% wasted work in its design.

The segmented cache has fixed attention/KV state, a hot region of dense
clusters with LRU replacement, and a cold region with neuron-level replacement.
The execution pipeline has gate I/O/calculation followed by up/down I/O/
calculation, using one I/O thread plus compute threads to break matrix barriers.

IMPORTANT EQUATIONS:
The paper's core scheduling cost is operational rather than a single new
equation: active cluster data is selected by a device-specific hot/cold
profile; corresponding gate/up/down records are transferred as a unit.

TRAINING REQUIRED:
Offline profiling on 10M+ Wikipedia/RefinedWeb tokens and device-specific
hot/cold classification/centroids. Predictor/placement preparation is not
free. The base model is not converted into a MoE.

INFERENCE MECHANISM:
Hot clusters run in the NPU-resident path; cold clusters are prefetched and
processed by CPU threads; segmented caches and pipeline overlap storage with
compute. Device-specific placement is central.

MEMORY BEHAVIOR:
One reported Mixtral47B setup at a 7 GB memory cap allocates approximately
1 GB non-FFN, 2.6 GB predictor, 2.7 GB scales and 0.4 GB runtime/cache in the
breakdown, leaving only about 1.8% of FFN weights cached. This illustrates how
metadata/predictor/scales can consume the memory budget.

I/O BEHAVIOR:
The paper reports UFS sequential around 4 GB/s versus PC SSD around 7.5 GB/s,
but random IOPS differ greatly. UFS 4 KB random behavior and a single command
queue make thread count important; multiple I/O cores can degrade throughput
by up to about 40%. The design uses cluster-sized transfers and one I/O thread
in the critical pipeline.

THROUGHPUT RESULTS:
On OnePlus12/Ace2, Mistral7B with 50% FFN offload is about 1.4 tok/s for
PowerInfer-2 versus 2.3 tok/s for LLM in a Flash in one comparison. A
Mixtral47B result is 11.68 tok/s at 19 GB and 2.13 tok/s at 7 GB, with a
reported 21.2x improvement over llama.cpp in its setup. The 7 GB point is the
more relevant warning: aggressive memory caps leave I/O dominant.

QUALITY RESULTS:
PowerInfer-2 reports quality comparable to llama.cpp in its evaluated models;
one Qwen2 average is about 78.38 versus 79.25 for llama.cpp. Exact task and
model details must be preserved when comparing.

HARDWARE:
OnePlus12/Ace2 smartphone, Arm CPU, NPU, UFS storage, unified/mobile memory.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Cluster-level coalescing, segmented cache, gate-first filtering, explicit
I/O/compute pipeline, and device-specific hot placement. Not portable NPU
throughput alone.

WHAT DID NOT WORK:
At low memory the cache is tiny and storage remains dominant. UFS random
reads and excessive I/O threads degrade. A generic CPU/SSD scheduler cannot
assume the same cache or queue behavior.

LIMITATIONS:
Mobile NPU/CPU and Android implementation; no Linux/x86 CPU-only result; the
predictor and scales consume a large fraction of a small cap; native sparse
models/modified model variants are used.

ASSUMPTIONS:
Activation clusters are stable; a hot subset is globally reusable; NPU can
run dense hot work; cluster reads amortize storage latency.

TRANSFER TO QWEN3.8-27B:
Copy neuron/group bundling, segmented hot/cold cache, gate-first filtering,
one-I/O-thread pipeline, and explicit small-cap memory accounting. Test
whether Qwen SwiGLU gate values can safely filter up/down groups; do not
assume mobile NPU placement or cluster quality.

TRANSFER TO LLAMA.CPP:
The segment/cache/pipeline concepts transfer; NPU scheduling and Android
memory mechanisms do not. A CPU implementation should start with fixed group
records and sequential ranges, then benchmark whether a sparse CPU kernel is
worth the bookkeeping.

WHAT WE SHOULD COPY:
[PRIOR ART] Cluster I/O unit; corresponding gate/up/down storage; segmented
cache; gate-first two-stage pipeline; device-specific profiling.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Mobile-specific hot/cold ratios, NPU/CPU split, and a memory
budget that hides predictor/scales costs in a different way.

OPEN QUESTIONS:
Can Qwen group records be made 8-32 KiB each without too much overfetch? Is a
CPU gate-first phase cheaper than reading both gate and up together? How much
predictor state can be kept below 8 GB?

[S05] SPARSE UPCYCLING

TITLE: Sparse Upcycling: Training Mixture-of-Experts from Dense Checkpoints
AUTHORS: Komatsuzaki et al.
YEAR: 2023
VENUE: ICLR 2023
URL: https://arxiv.org/abs/2212.05055 ; https://arxiv.org/html/2212.05055v2
CODE: Paper artifacts/checkpoint details are linked from the paper; no
      storage runtime is supplied.
RELEVANCE: high

PROBLEM:
Obtain a sparse MoE model without paying the full cost of training a large
MoE from random initialization.

KEY IDEA:
Copy a dense checkpoint into multiple identical experts, add a router, and
continue training. The copied initialization starts near the dense function;
continued training breaks symmetry and specializes experts.

ARCHITECTURE:
Experiments use T5 encoder/decoder models, with MoE layers inserted in a
subset of layers (for example six layers) and up to 32 experts. The decoder
uses top-k routing (often k=2); expert choice routing is used in some encoder
settings. The copied experts initially compute a redundant version of the
dense FFN.

ALGORITHM:
Dense weights are copied into each expert. Router weights are newly
initialized. Expert capacity and token routing follow standard sparse MoE
mechanics. The important initialization is copied weights, not random expert
weights. Identical copies create a symmetry problem: only continued training
with different routes/gradients can specialize them.

IMPORTANT EQUATIONS:
MoE output is the standard routed sum:
`y = sum_{e in TopK(router(x))} p_e(x) E_e(x)`.
At initialization, copied experts have `E_e ~= E_dense`, so selecting all or
appropriately weighted copies preserves the dense function, but top-k routing
and normalization can still change scale/output.

TRAINING REQUIRED:
Substantial continued training, reported in the range of roughly 10-60%
additional training budget depending on the experiment. The paper reports
that upcycling catches a sparse-from-scratch baseline at around 120% of the
dense training budget in relevant comparisons. More experts and more severe
changes increase the requirement.

INFERENCE MECHANISM:
A conventional router chooses experts. Active compute is generally kept near
the dense baseline while total capacity increases; this is the key mismatch
with our objective.

MEMORY BEHAVIOR:
Total parameters rise sharply. Illustrative T5 sizes are approximately
248M -> 2B, 783M -> 7.22B and 2.85B -> 26.26B for sparse variants. Expert
weights could be stored on SSD, but the paper does not do so.

I/O BEHAVIOR:
Not studied.

THROUGHPUT RESULTS:
No storage or single-token CPU wall-clock result. Sparse MoE FLOPs are lower
than a dense model of the same expanded capacity, not necessarily lower than
the original dense checkpoint.

QUALITY RESULTS:
Copied initialization is better than random under limited continued training;
random can catch up with more training. The results establish a practical
dense-to-MoE route, not a no-training or lower-active-FLOP conversion.

HARDWARE:
Large-scale TPU training, T5 models.

WHAT ACTUALLY CAUSED THE SPEEDUP:
The technique's value is training cost/quality and capacity scaling. It does
not demonstrate lower active compute than the source dense model.

WHAT DID NOT WORK:
Naively copying many experts without enough training leaves symmetry and
specialization problems. Applying sparse-upcycling as if it automatically
reduced source-model compute is incorrect.

LIMITATIONS:
It increases total parameters and commonly preserves comparable active FLOPs.
It requires continued training and routing changes. It is not a storage
layout or predictor solution.

ASSUMPTIONS:
Training data and compute are available to break symmetry; standard MoE
routing and capacity mechanisms are acceptable.

TRANSFER TO QWEN3.8-27B:
Borrow copied initialization and symmetry-breaking logic only if we decide to
train a genuine Qwen sparse expert model. To reduce active compute below
dense, expert width and/or top-k must also be reduced; that creates a quality
problem the original paper does not answer.

TRANSFER TO LLAMA.CPP:
Only after a trained sparse checkpoint exists: expert serialization/routing
could be supported. Upcycling itself gives no llama.cpp storage solution.

WHAT WE SHOULD COPY:
[PRIOR ART] Dense checkpoint copying as a stable initialization and explicit
measurement of additional training budget/symmetry.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Treat “sparse MoE” as “lower active compute than dense”; do
not multiply experts and then assume an 8 GB model.

OPEN QUESTIONS:
How much can copied group experts be narrowed before fine-tuning becomes
prohibitive? Could distillation from the dense Qwen3.8 model replace most of
the continued pretraining?

[S06] NVIDIA DENSE-TO-MOE UPCYCLING

TITLE: Upcycling Large Language Models into Mixture of Experts
AUTHORS: He et al. / NVIDIA authors
YEAR: 2024
VENUE: arXiv preprint
URL: https://arxiv.org/abs/2410.07524 ; https://ar5iv.labs.arxiv.org/html/2410.07524
CODE: No storage runtime in the paper record.
RELEVANCE: high

PROBLEM:
Convert billion-scale dense LLMs into fine-grained MoE models while retaining
quality and making training/inference tradeoffs explicit.

KEY IDEA:
Partition dense FFN weights into virtual groups, replicate them into many
fine-grained experts, scale the copied weights, and continue training. Virtual
groups preserve a structured path back to the dense matrix; routing chooses a
small number of groups.

ARCHITECTURE:
For dense groups G and replicated experts E, experts contain shards of the
dense FFN. Typical experiments compare E=8, group counts such as G=1 or 8,
and top-T routing such as T=2 or 8. The method includes experiments on
Nemotron-scale 2B/15B models and gated FFNs.

ALGORITHM:
Basic copy partitions and replicates weights. With topK-then-softmax,
normalization after selection can preserve the dense function only in a
particular all-replica limit. Softmax-then-topK retains absolute router
logit information and is empirically better in the paper. For squared ReLU,
the paper gives a scaling related to `T/(E G^2)` and rescales W1/W2 using a
cube-root factor; equal scaling is reported to work for SwiGLU in practice.
Auxiliary load balancing is around 1e-2 to 1e-3; too high harms quality.

IMPORTANT EQUATIONS:
The relevant initialization has a group/expert scale of the form
`scale ~ (E G^2 / T)^(1/3)` for the paired projections in one stated
derivation, with the inverse convention depending on which tensor is being
normalized. The exact paper equation must be followed in code; the key lesson
is that replicated fine-grained shards need explicit magnitude correction.

TRAINING REQUIRED:
Continued pretraining. One reported comparison uses one trillion examples/
tokens of dense continued training and then compares E8G8T8 or E8G1T2 MoE
variants. More experts have diminishing returns; 64 is generally useful while
128/256 add less.

INFERENCE MECHANISM:
Router logits -> chosen fine-grained experts -> gated FFN. T=2 costs more
than top-1; the paper studies quality/computation rather than SSD paging.

MEMORY BEHAVIOR:
Total capacity rises with replication. Fine-grained experts can make storage
units smaller, but metadata and random reads become harder. No RAM/SSD result.

I/O BEHAVIOR:
Not reported.

THROUGHPUT RESULTS:
Quality/computation tradeoffs and iso-FLOP comparisons are reported, not
single-stream CPU wall time or storage bytes/token.

QUALITY RESULTS:
Examples include dense continued val loss 1.377 / MMLU 65.3 versus E8G8T8
val loss 1.320 / MMLU 66.2, and E8G1T2 val loss 1.306 / MMLU 67.6 in the
reported comparisons. High load-balance loss harms quality; group granularity
around 8 is favorable; a shared expert did not clearly help.

HARDWARE:
NVIDIA-scale training, billion-scale models.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Conditional active experts at a fixed expanded capacity, plus fine-grained
routing. It does not show lower active compute than the original dense model
without a separate width/top-k choice.

WHAT DID NOT WORK:
Excessive expert granularity/routing overhead, too-high auxiliary loss,
naive scaling, and assuming more experts always improves quality.

LIMITATIONS:
Requires substantial continued training and does not solve storage. The
reported models are not Qwen3.8 and no x86/8 GB target is evaluated.

ASSUMPTIONS:
Large continued-training budget; standard MoE router; expert replication is
acceptable.

TRANSFER TO QWEN3.8-27B:
Borrow virtual-group initialization, explicit projection scaling and the
softmax-order comparison if a trained MoE branch is attempted. Gated SwiGLU
compatibility is encouraging. Do not assume the method gives a post-hoc
low-compute checkpoint; it is a training recipe.

TRANSFER TO LLAMA.CPP:
Expert granularity can inform on-disk group size, but routing/checkpoint
conversion must be implemented separately.

WHAT WE SHOULD COPY:
[PRIOR ART] Virtual groups, projection scaling, load-balance loss sweeps,
granularity ablations, and explicit active-compute accounting.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Continued-training results as evidence for training-free
conversion or SSD throughput.

OPEN QUESTIONS:
Can a tiny distillation run reproduce useful virtual-group specialization?
Does fine-grained replication make SSD reads too random for a CPU decoder?

[S07] DEJAVU

TITLE: Deja Vu: Contextual Sparsity for Efficient LLMs at Inference Time
AUTHORS: Liu et al.
YEAR: 2023
VENUE: ICML 2023 / arXiv 2023
URL: https://arxiv.org/abs/2310.17157 ; https://proceedings.mlr.press/v202/liu23am/liu23am.pdf
CODE: https://github.com/FMInference/DejaVu, commit ee902c1
RELEVANCE: high

PROBLEM:
Use input-dependent sparsity in a dense pretrained LLM without requiring a
MoE architecture up front.

KEY IDEA:
Predict which attention heads and MLP parameters will matter for the current
context, then run structured sparse kernels. Prediction is asynchronous and
lookahead exploits the slow change of consecutive hidden states.

ARCHITECTURE:
Contextual sparsity selects attention heads and MLP intermediate rows/columns.
The sparse MLP is `MLP_S(y)=sigma(y W1_S) W2_S^T`. For OPT-175B the paper
reports up to about 80% head sparsity and 95% MLP parameter sparsity in a
tested regime.

ALGORITHM:
The predictor is a two-layer fully connected classifier, not online nearest
neighbor search. HNSW/FAISS were too slow in the cited comparison (over 10 ms
and over 4 ms), while a small MLP was about 0.2 ms for OPT-175B. Code uses a
low-rank/parallel classifier: embedding -> low-rank dimension (example D=1000)
-> output logits. Training uses memmapped predictor data, BCE with weighted
positives, AdamW, default 20 epochs, lr 1e-4 and roughly 400k samples in the
repository training script. The paper describes a 500 C4 sample setup for
some predictor construction; exact data scale differs by experiment.

The async predictor estimates the next layer's set from the current output.
An informal slow-change argument is that if `||y_l-y_{l-1}|| <= epsilon`, a
MaxIP-style set remains close enough for high recall. The real implementation
runs the predictor on a separate CUDA stream and synchronizes with an event.

Attention prediction can save selected KV heads and token embeddings so a
missing head can be recomputed later. Sparse MLP kernels gather W1 rows and
W2 columns; the repository uses a layout chosen for coalesced indexed loads.

IMPORTANT EQUATIONS:
`S_A^l = SP_A^l(y_l)` and `S_M^l = SP_M^l(MHA(y_l))` are the native current-
layer predictor sets. The asynchronous lookahead uses current activations to
predict `S_A^(l+1), S_M^(l+1)` while current work proceeds.

TRAINING REQUIRED:
Small predictor training/calibration on activation/mask labels. The base LLM
weights remain unchanged.

INFERENCE MECHANISM:
Predict mask, gather selected rows/columns, run fused sparse kernels. Predictors
are launched early and hidden behind current MLP/attention work where the GPU
allows it. This hides predictor cost but does not automatically hide SSD reads.

MEMORY BEHAVIOR:
Sparse kernels avoid loading all selected-unselected rows into GPU memory.
The paper's primary setting is large A100 memory; it does not maintain an SSD
resident cold pool.

I/O BEHAVIOR:
The paper is about GPU memory traffic, not flash. Its fused indexing avoids a
separate indexing pass that would multiply weight traffic. No SSD bytes/token.

THROUGHPUT RESULTS:
Batch 1 on 8 A100 80 GB GPUs with NVLink, FP16, prompt lengths 128-1024.
At a reported regime of roughly 75% sparsity, DejaVu is 1.8-2x faster than
FasterTransformer and 4.8-6x faster than Hugging Face in the paper's setup.
These are actual wall-clock results but not CPU/SSD decode.

QUALITY RESULTS:
OPT-175B/66B/30B tests report no accuracy drop at selected regimes in the
paper tables, with MLP around 85% sparse and attention around 50% sparse for
one OPT-175B setting. Predictor recall varies by depth; the paper reports
shallow MLP over 99% improving to roughly 93%, and attention middle layers
around 93% with shallow/deep around 99% in one analysis. W4A16 compatibility
is discussed and tested without compounding errors in the table.

HARDWARE:
8x NVIDIA A100 80 GB NVLink; CUDA/Triton custom kernels.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Structured indexing kernels, high mask recall, predictor overlap, reduced
GPU memory traffic and attention/MLP sparsity. Not merely sparse FLOPs.

WHAT DID NOT WORK:
Nearest-neighbor search predictors were too slow; predictors run too late if
not overlapped; low recall causes quality errors; GPU kernels are necessary.

LIMITATIONS:
The models/activations are mostly older dense ReLU/GELU-era LLMs. It does not
show storage reads, x86 CPU kernels, Qwen3.8 hybrid blocks or <8 GB RAM. A
per-layer predictor can be too late to fetch from SSD.

ASSUMPTIONS:
Temporal/context locality; predictor overhead can overlap current GPU work;
indexed sparse matrix kernels are efficient; mask errors are rare enough.

TRANSFER TO QWEN3.8-27B:
Use contextual sparsity as a router without converting all MLPs to MoE. Train
or construct an early shared predictor and measure gated contribution masks.
Borrow lookahead, but move the prediction horizon earlier than DejaVu's
within-layer operation so storage reads can complete.

TRANSFER TO LLAMA.CPP:
Architecture/predictor idea transfers. CUDA streams/Triton kernels do not.
On CPU, predictor cost and gather overhead must be measured alongside I/O.

WHAT WE SHOULD COPY:
[PRIOR ART] Shallow predictors, async lookahead, structured W1/W2 indexing,
recall-first evaluation, and predictor overhead accounting.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Per-layer-late prediction for SSD, GPU speedups as CPU
results, or head sparsity without a Qwen hybrid-quality test.

OPEN QUESTIONS:
Can one early predictor predict all 64 Qwen MLP layers accurately enough?
Does a group-level mask improve storage locality without losing too much
recall? Can predictor execution overlap CPU attention rather than GPU work?

[S08] POWERINFER

TITLE: PowerInfer: Fast Large Language Model Serving with a Consumer-grade GPU
AUTHORS: Song et al.
YEAR: 2023
VENUE: MLSys/ arXiv 2023
URL: https://arxiv.org/abs/2312.12456 ; https://arxiv.org/pdf/2312.12456
CODE: https://github.com/SJTU-IPADS/PowerInfer
RELEVANCE: high

PROBLEM:
Serve models larger than consumer GPU memory by exploiting nonuniform neuron
activation and a CPU/GPU split.

KEY IDEA:
Activation frequencies follow a power-law. Place globally hot neurons on GPU
and context-dependent cold neurons on CPU; use an online predictor and sparse
neuron-aware operators.

ARCHITECTURE:
The method keeps hot neurons resident on the GPU and computes cold neurons on
the CPU, then merges results. It does not convert the model to MoE and does
not use SSD as the cold pool.

ALGORITHM:
An offline profiler measures activation frequencies on about one million
Wikipedia tokens, while an online predictor handles contextual variation.
Placement is formulated using activation frequency/impact and an ILP-like
policy. Sparse operators handle selected neuron rows/columns. Predictor sizes
are reported around 4.88-8.68% of model parameters and training can take
hours on multiple GPUs.

IMPORTANT EQUATIONS:
The useful empirical rule is the activation frequency/impact priority
`v_i ~= f_i` for hot placement. It is a placement heuristic, not a general
quality guarantee. Sparse FFN work is grouped by active neuron indices and
merged with hot GPU output.

TRAINING REQUIRED:
Offline hot/cold profiling and predictor training. No dense-to-MoE training.

INFERENCE MECHANISM:
GPU hot dense path + CPU cold sparse path + synchronization/merge. Batch 1 is
the target in the main consumer-GPU comparison; speedup falls with larger
batches.

MEMORY BEHAVIOR:
Hot neurons consume GPU memory; cold weights remain CPU-resident. This proves
the “resident hot core + external cold pool” abstraction but not SSD residency.

I/O BEHAVIOR:
PCIe transfers rather than SSD. False predictor choices and synchronization
are important; the paper reports examples where a hot neuron can be predicted
inactive.

THROUGHPUT RESULTS:
PC-High uses i9-13900K, 8 cores, 192 GB RAM and RTX4090 24 GB; PC-Low uses
i7-12700K, 8 cores, 64 GB RAM and RTX2080Ti 11 GB. INT4 batch-one averages
are about 13.2 tok/s on the high-end setup, with peak 29.08 and average
speedup around 2.89 (maximum about 4.28); OPT-175B is close to 2 tok/s and
about 2.66x in the reported setting. These are not storage measurements.

QUALITY RESULTS:
The paper reports good quality preservation across supported models while
using hot/cold placement. LLaMA2/ReGLU/SwiGLU activation distributions are
measured, not assumed.

HARDWARE:
Consumer NVIDIA GPUs plus x86 CPUs and PCIe, not CPU-only SSD.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Hot global reuse, sparse cold operators, predictor placement and avoiding
GPU-memory capacity failure. It explicitly exploits the activation distribution.

WHAT DID NOT WORK:
Predictor mismatch and synchronization can erase gains. The CPU/GPU split is
not a flash scheduler.

LIMITATIONS:
The reported hot percentages differ by activation: ReLU OPT30B about 26%
neurons account for 80% activations, LLaMA2 ReGLU70B about 43%, and SwiGLU
LLaMA270B about 69% in one table; across-model percentages also differ. These
are global frequency observations, not per-token safe sparsity. Predictor
training and PCIe/GPU assumptions do not transfer unchanged.

ASSUMPTIONS:
Global hot neurons are stable across tasks; cold work can be sparse on CPU;
GPU hot capacity and PCIe transfers are available.

TRANSFER TO QWEN3.8-27B:
Strongly supports a resident hot core plus SSD cold pool, but global hot
groups should be used as cache candidates, not as the entire route. Profile
Qwen3.8 gated groups and retain high-frequency groups in RAM.

TRANSFER TO LLAMA.CPP:
CPU sparse operators, frequency-based cache selection and predictor error
accounting transfer. GPU/PCIe placement does not.

WHAT WE SHOULD COPY:
[PRIOR ART] Power-law/hot-core measurement, offline profile plus online
prediction, impact-aware placement, and explicit merge/synchronization costs.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Hot percentages as guaranteed per-token activity or GPU
speedup as SSD performance.

OPEN QUESTIONS:
How much of Qwen3.8's active set is globally hot? Does hot-core residency
lower SSD reads enough for 10-20 tok/s? How should cache placement account for
the different 48 linear and 16 full-attention layers?

[S09] SPARSEGPT

TITLE: SparseGPT: Massive Language Models Can be Accurately Pruned in One-Shot
AUTHORS: Frantar and Alistarh
YEAR: 2023
VENUE: ICML 2023
URL: https://arxiv.org/abs/2301.00774 ; https://proceedings.mlr.press/v202/frantar23a/frantar23a.pdf
CODE: https://github.com/IST-DASLab/sparsegpt
RELEVANCE: medium-high

PROBLEM:
Remove static weight redundancy from very large LMs using a single calibration
pass rather than retraining.

KEY IDEA:
Use a Hessian/OBS-inspired one-shot update to choose a sparse mask and
reconstruct remaining weights. It supports unstructured sparsity and some
structured N:M patterns.

ARCHITECTURE:
Layerwise pruning treats each linear weight matrix independently. It is not
contextual and does not create experts.

IMPORTANT EQUATIONS:
`min_{M,W} ||W X - (M * W_hat) X||_2^2` is the layer reconstruction
objective; OBS-style deletion uses
`delta_m = -w_m/[H^-1]_{mm} * H^-1_{:,m}` and estimated error
`epsilon_m = w_m^2/[H^-1]_{mm}`.

ALGORITHM:
The layer objective is approximately
`min_{M,W} ||W X - (M * W_hat) X||_2^2`.
For a fixed mask, reconstruction uses a Hessian inverse. A stated OBS-style
deletion update is
`delta_m = -w_m / [H^-1]_{mm} * H^-1_{:,m}`
with estimated deletion error
`epsilon_m = w_m^2 / [H^-1]_{mm}`.
Calibration uses a small multiple of the layer input dimension and block
processing (often block 128); the core complexity is cubic in hidden dimension
for the Hessian operations.

TRAINING REQUIRED:
No gradient training, but calibration activations are required.

INFERENCE MECHANISM:
Static sparse weights are used for every token. There is no router/predictor.

MEMORY BEHAVIOR:
Can reduce stored weight size and potentially resident RAM. Unstructured
sparsity may need specialized kernels; 2:4/4:8 is more hardware-friendly.

I/O BEHAVIOR:
Static reduction lowers every future read but does not reduce context-dependent
working-set volume. A structured packed format is necessary for SSD efficiency.

THROUGHPUT RESULTS:
The paper emphasizes perplexity and sparsity; exact single-stream x86 SSD
throughput is not a result.

QUALITY RESULTS:
OPT/BLOOM around 50-60% unstructured sparsity is reported with small
perplexity changes. Example OPT-175B PPL is about 8.21 at 50% versus dense
8.35; 4:8 about 8.45 and 2:4 about 8.74 in one table.

HARDWARE:
Large-model calibration and sparse hardware experiments; not our storage
runtime.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Permanent parameter removal/structured hardware sparsity, not contextual
selection.

WHAT DID NOT WORK:
Unstructured masks can fail to translate to wall-clock CPU speedups; high
structured sparsity costs quality; it cannot distinguish “inactive now” from
“needed later.”

LIMITATIONS:
It is static pruning, not a solution to conditional SSD residency. It may
also interact badly with Qwen gated rows if the three aligned projections are
pruned independently.

ASSUMPTIONS:
Calibration distribution represents deployment; remaining weights can be
computed efficiently.

TRANSFER TO QWEN3.8-27B:
Use as an optional permanent first stage to reduce all group records and the
resident floor. Apply jointly or consistently to gate/up/down structure. Do
not treat it as a replacement for contextual routing.

TRANSFER TO LLAMA.CPP:
N:M or block-structured static packing is more plausible than arbitrary masks.
It could reduce the amount of every SSD group, but kernel/layout work remains.

WHAT WE SHOULD COPY:
[PRIOR ART] Calibration-aware reconstruction and the distinction between
weight redundancy and contextual inactivity.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Unstructured sparsity as a guaranteed CPU/SSD wall-clock
gain or independent pruning of gated projections.

OPEN QUESTIONS:
Can static group-aware pruning reduce Qwen's 9.6 GB MLP pool enough to make a
dynamic SSD design feasible without consuming the quality budget first?

[S10] SWITCH TRANSFORMERS

TITLE: Switch Transformers: Scaling to Trillion Parameter Models with Simple and Efficient Sparsity
AUTHORS: Fedus, Zoph and Shazeer
YEAR: 2021/2022
VENUE: JMLR 2022
URL: https://arxiv.org/abs/2101.03961 ; https://jmlr.org/papers/v23/21-0998.html
CODE: No storage implementation used.
RELEVANCE: high for MoE mechanics

PROBLEM:
Scale parameter capacity with sparse expert routing while keeping per-token
compute and communication manageable.

KEY IDEA:
Top-1 routing: each token is sent to one expert, minimizing router and
communication cost relative to top-2 MoE.

ARCHITECTURE:
Router logits `h = W_r x`, probabilities `p_i=softmax(h)_i`; selected expert
output is `E_argmax(p)(x)` with a gating scale. Capacity is bounded per expert.

ALGORITHM:
Expert capacity is approximately
`capacity = tokens_per_batch / num_experts * capacity_factor`.
Overflow tokens can be dropped and passed through/residual-connected. The
load-balance auxiliary loss is
`L_aux = alpha * N * sum_i f_i P_i`, where `f_i` is the fraction of tokens
dispatched to expert i and `P_i` is mean router probability for i. The paper
uses alpha near 1e-2 as a common setting, with sweeps. Router computation is
performed in float32 for stability; router initialization scale is reduced.

TRAINING REQUIRED:
Designed for end-to-end MoE training. Expert collapse/imbalance must be
managed during training.

INFERENCE MECHANISM:
Top-1 route with fixed capacity. This makes active compute predictable at
batch scale, but a single-token decode cannot exploit capacity balancing in
the same way as large-batch training.

IMPORTANT EQUATIONS:
`h = W_r x`, `p_i=softmax(h)_i`, and the capacity constraint is approximately
`capacity = tokens_per_batch / num_experts * capacity_factor`. The balance loss
is `L_aux = alpha * N * sum_i f_i P_i`; overflow/drop behavior is part of the
runtime semantics.

MEMORY BEHAVIOR:
Only selected expert weights need to be active in principle, making the
mechanism attractive for SSD. Capacity buffers and expert metadata still
matter.

I/O BEHAVIOR:
Not studied. Token dropping is unacceptable for a quality-sensitive single
stream unless a fallback is guaranteed.

THROUGHPUT RESULTS:
Training scaling/throughput on TPU; no CPU/SSD single-token result.

QUALITY RESULTS:
The paper demonstrates competitive quality at scale, subject to routing
stability and capacity/drop settings.

HARDWARE:
TPUv3 training, large distributed batches.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Top-1 conditional compute and reduced communication relative to dense scaling.

WHAT DID NOT WORK:
Router instability, expert imbalance/collapse and token overflow. Capacity
factor above one wastes memory/compute; too low drops tokens.

LIMITATIONS:
Single-token storage inference has no natural token pool to balance. An
auxiliary loss learned on batches does not guarantee a stable one-token route.

ASSUMPTIONS:
Large training batches and continued end-to-end optimization; overflow can
be tolerated or is rare.

TRANSFER TO QWEN3.8-27B:
Use router logits/top-k/aux-loss mechanics only for a trained branch. For
post-hoc conversion, a deterministic group predictor plus exact fallback is
safer than token dropping.

TRANSFER TO LLAMA.CPP:
Top-1 expert selection can map to a small number of SSD group reads, but
capacity-factor logic should not be copied blindly to batch-one decode.

WHAT WE SHOULD COPY:
[PRIOR ART] Float32 router logits, explicit balance diagnostics, capacity and
overflow accounting, and the distinction between top-k routing and capacity.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Token dropping or batch-oriented load balance for a single
user unless a quality-preserving fallback exists.

OPEN QUESTIONS:
Could routing be constrained to storage-friendly contiguous groups without
destroying the learned function? Can a one-token stream use a small persistent
route history as its balancing signal?

[S11] EXPERT CHOICE ROUTING

TITLE: Mixture-of-Experts with Expert Choice Routing
AUTHORS: Zhou et al.
YEAR: 2022
VENUE: NeurIPS 2022
URL: https://arxiv.org/abs/2202.09368 ; https://ar5iv.labs.arxiv.org/html/2202.09368
CODE: Paper method; no storage runtime.
RELEVANCE: medium-high

PROBLEM:
Avoid token-choice load imbalance and token dropping in MoE training.

KEY IDEA:
Experts choose their top-k tokens instead of each token choosing experts.
Each expert receives a fixed-capacity bucket, giving perfect expert capacity
balance and a variable number of experts per token.

ARCHITECTURE:
For an expert capacity factor, each expert selects tokens with highest router
affinity. A token can be selected by zero, one, or several experts; expert
capacity is fixed.

ALGORITHM:
The router creates an expert-by-token score matrix and top-k selection per
expert. It avoids the usual auxiliary balance loss. Reported token
distribution includes a majority with 1-2 experts, about 23% with 3-4 and
about 3% with more in one analysis. Capacity-factor 2 can have active work
similar to top-2 token routing.

IMPORTANT EQUATIONS:
The conceptual route is `I_e = TopK_tokens(score_e,:)`, with fixed `|I_e|`.
This reverses the usual `e = TopK_experts(score_token,:)` direction.

TRAINING REQUIRED:
End-to-end MoE training, large batches and TPU-scale experiments.

INFERENCE MECHANISM:
Variable experts/token. That can be useful when token difficulty varies, but
expert choice needs a population of tokens to fill buckets.

MEMORY BEHAVIOR:
Fixed expert buckets simplify training buffer allocation, not SSD single-token
reads.

I/O BEHAVIOR:
Not studied. For a single autoregressive token, expert-choice has too little
token population and can require awkward microbatch/history buffering.

THROUGHPUT RESULTS:
The paper reports over 2x convergence improvements in 8B/64E experiments and
large TPU training, not SSD inference.

QUALITY RESULTS:
Competitive quality and improved training efficiency under the evaluated
large-batch settings.

HARDWARE:
512 TPUv4-scale training.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Balanced training batches and no token overflow, not lower single-token I/O.

WHAT DID NOT WORK:
The routing direction is a poor direct fit for one-token decode and variable
storage traffic.

LIMITATIONS:
No evidence for x86/SSD, no post-hoc dense conversion, and no deterministic
small active set for a single user.

ASSUMPTIONS:
Large batches can be formed and tokens can be assigned globally.

TRANSFER TO QWEN3.8-27B:
Useful only as a training/load-balance concept. A storage scheduler could
borrow fixed capacity buckets offline, but runtime route should remain
token-choice for single-stream decode.

TRANSFER TO LLAMA.CPP:
Not a direct runtime design.

WHAT WE SHOULD COPY:
[PRIOR ART] Fixed-capacity thinking and analysis of variable experts/token.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Expert-choice dispatch for batch-one SSD fetches.

OPEN QUESTIONS:
Could a short rolling microbatch of speculative tokens make expert-choice
useful, or would KV/latency constraints outweigh it?

[S12] DYNAMOE

TITLE: From Dense to Dynamic: Token-Difficulty Driven MoEfication of Pre-Trained LLMs
AUTHORS: Nishu et al.
YEAR: 2025
VENUE: arXiv preprint
URL: https://arxiv.org/abs/2502.12325 ; https://arxiv.org/html/2502.12325v1
CODE: No public storage/runtime implementation identified in the paper record.
RELEVANCE: high

PROBLEM:
Turn a dense pretrained LLM into a dynamic MoE whose compute depends on token
difficulty, using only limited additional training.

KEY IDEA:
Reorder MLP neurons by activation magnitude and create nested experts of
increasing width. A router predicts the smallest expert whose output is close
to the full dense MLP output. Attention is frozen.

ARCHITECTURE:
Only MLPs are changed. For E experts and dense width H, expert e has nested
width `H_e = floor((e+1)/E * H)`; the final expert is full width. The same
prefix rows/columns are used, so storage can naturally be prefix/range based.
The reported 4-expert sizes are 0.25H, 0.5H, 0.75H and H.

IMPORTANT EQUATIONS:
`S_{b,e}=<Y_e,Y_full>/<Y_full,Y_full>` labels the smallest nested expert
whose output is sufficiently close to the full dense output. The router loss
must be combined with language-model loss to avoid route collapse.

ALGORITHM:
Run all nested experts and the full dense output on calibration data. Define
similarity `S_{b,e}=<Y_e,Y_full>/<Y_full,Y_full>` and label each token with the
smallest e satisfying threshold theta. Train a two-linear-layer router
(hidden U=256) with about 33.6M parameters across layers, around 0.51% of the
base model. The loss combines language modeling and router terms, with one
reported `lambda_LLM=.2, lambda_router=1`.

TRAINING REQUIRED:
Reported continued fine-tuning uses about 10B Falcon RefinedWeb tokens,
AdamW lr1e-5. Without the router loss, the router can collapse to one expert
per layer. Neighboring expert misclassifications occur.

INFERENCE MECHANISM:
Predict token difficulty, select a nested width, and run prefix rows/columns.
This is attractive for storage because the selected data can be a contiguous
prefix, but it does not itself implement asynchronous SSD streaming.

MEMORY BEHAVIOR:
Nested experts duplicate/organize dense weights rather than materially
shrinking the full disk model. Prefix storage and a resident hot prefix are
possible.

I/O BEHAVIOR:
Not measured. No SSD bytes/token or cache/prefetch results.

THROUGHPUT RESULTS:
The paper explicitly does not provide a real deployment speed benchmark; it
reports compute/capacity and quality, including a claimed 1/9 Flextron cost
in its framing. This must not be treated as x86 wall-clock speed.

QUALITY RESULTS:
For Mistral7B, base average scores are about 77.8 on a 4-task group and 74.2
on a 7-task group. DynaMoE at theta .9 is about 74.0/70.1, theta .8 about
70.5/66.5 and theta .7 about 67.7/64.0, with parameter/compute points around
6.0/5.1/4.6B in the table. The quality cost is substantial at aggressive
sparsity.

HARDWARE:
Training/evaluation framework; no storage hardware result reported.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Nested width reduction by token difficulty in the theoretical/compute sense.
No evidence yet of storage overlap or sparse CPU kernel speed.

WHAT DID NOT WORK:
Router loss removal caused collapse; neighboring width mistakes and threshold
tradeoffs limit quality; no end-to-end deployment result.

LIMITATIONS:
10B-token fine-tuning is not a cheap post-hoc conversion. Results are Mistral7B
and not Qwen3.8 gated hybrid blocks. It does not show SSD residency.

ASSUMPTIONS:
MLP output similarity is a good token-difficulty label; nested prefixes are
good approximations; attention can remain dense/frozen.

TRANSFER TO QWEN3.8-27B:
Borrow nested/prefix group layout and output-similarity labels. It may make
SSD reads sequential and cache-friendly. Expect a separate Qwen gated trace
and distillation/fine-tuning, and do not assume 10B tokens are acceptable.

TRANSFER TO LLAMA.CPP:
Prefix groups are easy to range-read and can use fixed slots. Router and
quality validation still need implementation.

WHAT WE SHOULD COPY:
[PRIOR ART] Nested groups; full-output similarity labels; explicit token-
difficulty route; router-loss anti-collapse test.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Claimed compute cost as actual speed, or its quality/ratio
as a Qwen3.8 prediction.

OPEN QUESTIONS:
Can an output-aware group order be found for SwiGLU that preserves dense
quality at 20-40% width? Does nested prefix selection reduce random SSD I/O
enough to offset overfetch?

[S14] SVD CONTEXTUAL SPARSITY PREDICTORS

TITLE: SVD Contextual Sparsity Predictors for Fast LLM Inference
AUTHORS: Serbin, Koshkin, Sun, Bistrigova and Korikov
YEAR: 2026
VENUE: arXiv preprint
URL: https://arxiv.org/abs/2603.14110 ; https://arxiv.org/html/2603.14110v1
CODE: No implementation repository verified during this pass.
RELEVANCE: high

PROBLEM:
Avoid training a large neural sparsity predictor while retaining contextual
FFN sparsity for edge inference.

KEY IDEA:
Approximate each gate projection with a data-whitened low-rank SVD, then add
per-neuron calibrated thresholds. The predictor is affine plus a Heaviside
mask and uses only a few thousand calibration tokens.

ARCHITECTURE:
The method modifies only ReGLU/dReLU FFNs. For
`FFN(x)=W_down(ReLU(W_gate x) * (W_up x))`, the mask is predicted from a
low-rank approximation of W_gate. Gate and up are executed sequentially:
predicted positives are checked by the real gate, then false positives are
removed before up/down.

IMPORTANT EQUATIONS:
`P(x)=H(A B x+b)` with whitened rank-r factors `A,B`; sequential sparse work
is `r(d+D) + d(1-s)D + 2d(1-s')D` versus dense `3dD`. The damage proxy is
`w_i^t=|ReLU(gate_i)*up_i|^2 ||down_:,i||^2`.

ALGORITHM:
Given calibration X, form a Cholesky whitening S from `X X^T`, factor
`W_gate S = U Sigma V^T`, and use rank r:
`A = U_:,:r Sigma_:r,:r`, `B = V_:r,: S^-1`, predictor `P(x)=H(A B x+b)`.
Threshold/bias b is greedily calibrated. Importance for neuron i/sample t is
`w_i^t = |ReLU(gate_i) * up_i|^2 ||down_:,i||^2`; thresholds are increased by
the smallest empirical damage until a target sparsity/drop budget is reached.
The appendix gives a deterministic residual/error bound based on the SVD
residual and bias.

The sequential sparse-compute complexity is reported as
`r(d+D) + d(1-s)D + 2d(1-s')D`, versus dense `3dD`, where s is predicted and
s' realized sparsity. The authors explicitly warn that FLOP reduction does
not directly imply wall-clock speedup.

TRAINING REQUIRED:
No predictor gradient training; SVD, whitening and greedy threshold
calibration use a small calibration set. The base evaluated models are already
sparse/ReGLU/dReLU models, so this is not proof for unmodified Qwen SwiGLU.

INFERENCE MECHANISM:
Predict at the start of each FFN; compute gate; remove false positives; then
compute only remaining up/down. CUDA custom kernels and CANN executors are
provided in the paper's evaluation.

MEMORY BEHAVIOR:
Predictor storage is low-rank and per-neuron bias. No SSD working-set design.

I/O BEHAVIOR:
No flash results. Sequential gate/up is potentially useful for reducing cold
reads, but if gate itself must be fetched it still needs a storage schedule.

THROUGHPUT RESULTS:
Single RTX3090 GPU, fp16/vLLM, and Ascend 310P3. E2E includes prefill plus
200-token generation. On ProSparse-LLaMA2-7B, reported speedups are about
1.61-1.71x at 40-70% target sparsity; TurboSparse-Mistral about 1.67-1.84x;
SparseQwen2-7B about 1.78-1.86x. The best reported benchmark average drops
are under roughly 1.4 points at the high settings, with many under 1 point.

QUALITY RESULTS:
SparseQwen2-7B dense average 65.84; SVDP averages about 65.41/65.20/65.13/
64.49 at target s=.4/.5/.6/.7. The paper reports up to 1.8x E2E and less
than 1% degradation in selected complex math/code settings, but results use
already sparse/dReLU/ReGLU models.

HARDWARE:
RTX3090 and Ascend 310P3, CUDA/CANN, no x86 CPU or NVMe result.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Low-rank predictor plus sequential gate validation and custom sparse kernels.

WHAT DID NOT WORK:
Naive SVD thresholding caused quality loss; whitening and bias calibration
were required. The paper notes predictor pipelining may be infeasible on some
hardware platforms.

LIMITATIONS:
ReGLU/ReLU/dReLU assumption; unmodified SiLU gate is not an exact zero mask;
GPU/NPU kernels; no storage. Predictor rank and calibration may be large for
Qwen's D=17408 if recall must be very high.

ASSUMPTIONS:
Gate projection is low-rank enough; calibrated scores generalize; exact gate
validation can safely filter false positives.

TRANSFER TO QWEN3.8-27B:
Test a Qwen-specific low-rank gate predictor as a training-light option, but
use continuous contribution thresholds, not binary ReLU correctness. A gated
sequential path may first read/predict gate groups, then fetch up/down only
for surviving groups. This could be especially useful for SSD bytes/token.

TRANSFER TO LLAMA.CPP:
The affine low-rank predictor is CPU-friendly in principle. Its value depends
on a sparse/group CPU kernel and storage-aware two-stage reads, neither of
which is provided.

WHAT WE SHOULD COPY:
[PRIOR ART] Data-aware low-rank gate predictor, per-neuron damage-aware
threshold calibration, sequential gate->up/down testing and explicit FLOP/
wall-clock distinction.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] ReGLU exact-zero guarantees or GPU speedups as Qwen SwiGLU
claims.

OPEN QUESTIONS:
Does a low-rank approximation predict Qwen3.8 gated contribution groups with
high recall? Is a two-stage SSD read cheaper than reading bundled gate+up at
once? Can the predictor be quantized and kept resident below 8 GB?

[S18] NEUROPREFETCHER

TITLE: NeuroPrefetcher: Storage-Aware Sparse LLM Inference via Delta Prefetching
AUTHORS: Nobel Dhar et al.
YEAR: 2026
VENUE: ICPP 2026 paper / arXiv preprint
URL: https://arxiv.org/abs/2608.22643 ; https://arxiv.org/html/2608.22643v1
     https://doi.org/10.1145/3832810.3832862
CODE / ARTIFACT: https://github.com/nobeldhar/llm-activation-sparsity
RELEVANCE: very high

PROBLEM:
Run a model larger than resident memory when dynamic sparse MLP weights must
come from NVMe during autoregressive decode.

KEY IDEA:
Predict all downstream MLP gate/up active masks with one resident predictor,
cluster masks into a centroid vocabulary, store neuron records contiguously,
and fetch only mask deltas between adjacent tokens. Reuse fixed slots instead
of compacting the entire working set each token.

ARCHITECTURE:
Jetson AGX Orin 32 GB unified LPDDR5, 12 Arm A78AE cores, Ampere GPU and
Samsung 990 Pro NVMe. Mistral7B is about 7.24B parameters/13.49 GiB fp16,
32 layers, hidden4096/intermediate14336. A dense prefix fits in the cap;
the sparse suffix has active row buffers. Embeddings/head/final norm,
attention/projections, per-layer norms, predictor and centroid data stay
resident. The paper says layers 1-31 are predicted; its dense/sparse handling
of down is described in a way that should be checked carefully because the
main layout and delta text both discuss active down-transposed columns.

ALGORITHM:
Threshold small activation values per layer and cluster binary gate/up masks
into K=512 centroids. The predictor uses token embedding, pre-attention norm,
a 128-dimensional attention sketch, post-attention norm scalar and layer-0
gate centroid ID. It has four feature projection blocks to width 512, a
centroid embedding, a four-block residual MLP trunk and gate/up heads for each
later layer. It is about 206.8M parameters / 413.6 MB fp16, 2.86% of base.

For current active set A_t and previous A_(t-1):
`D_in = A_t - A_(t-1)`
`D_out = A_(t-1) - A_t`.
Only D_in is read; D_out slots are reusable. A fixed Kmax slot map avoids
compaction. The first token requires a full predicted set.

Storage records are repacked gate/up/downT for each intermediate neuron,
approximately 24.5 KiB per fp16 Mistral neuron record (3*4096*2 bytes plus
alignment in the described layout). Active IDs are sorted and adjacent ranges
coalesced. Linux io_uring with O_DIRECT, QD256, page-aligned registered/mapped
staging and a fused deinterleave/scatter kernel are used. Some staging/cache
coherence is Jetson-specific.

IMPORTANT EQUATIONS:
Delta traffic is proportional to `|D_in| * bytes_per_neuron`, not
`|A_t| * bytes_per_neuron`, when reuse holds. Their mask thresholds and
centroid/predictor equations are implementation-specific; the important
system equation is the delta set above.

TRAINING REQUIRED:
Mask clustering and predictor training; the predictor is 2.86% of base in
the reported setup. The model itself is an existing sparse-activation setup,
not a dense Qwen3.8 post-hoc conversion.

INFERENCE MECHANISM:
Predict future masks from a single resident predictor, issue async O_DIRECT
delta reads, scatter into fixed buffers, then execute sparse MLP. A dense
prefix is used to reduce storage exposure under a memory cap.

MEMORY BEHAVIOR:
Evaluates caps around 9-17 GiB and reports a substantial dense prefix plus
sparse suffix. At 9 GB, predictor and fixed resident state consume a large
fraction; active working buffers are bounded.

I/O BEHAVIOR:
At 14.8 GiB, NVMe reads are about 103 MiB/token; at 9 GiB, just under 1 GiB/
token. 80-87% of latency is NVMe in reported cap settings. Active-mask
persistence is about 82-85% token-to-token, making delta reuse the dominant
I/O reduction.

THROUGHPUT RESULTS:
At a 14 GiB-ish cap, NeuroPrefetcher is reported around 3.22 tok/s versus
llama.cpp about 0.34 tok/s in the model-exceeds-memory regime. At 9 GiB,
about 1.7 tok/s; at 13.2 GiB, about 3.7 tok/s. When llama.cpp also fits near
13.9/14.8 GiB, its throughput is roughly 5.9/7.7 tok/s and the advantage
narrows to about 1.2/1.1x. This is far below a universal 10-20 tok/s target.

QUALITY RESULTS:
The abstract reports preserving roughly 92-96% of dense accuracy; evaluation
uses WikiText2 perplexity and 10-shot HellaSwag on Llama3-8B/related models.
Centroid/predictor layer decisions are reported around 99% accuracy, but
quality depends on threshold/clustering. It is not Qwen3.8 quality evidence.

HARDWARE:
Jetson AGX Orin/Arm/NVIDIA unified memory, Samsung 990 Pro NVMe, CUDA/IO
Uring/O_DIRECT. Not CPU-only x86.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Delta prefetch, 82-85% active-set reuse, contiguous neuron records, fixed
slots, O_DIRECT/queueing, fused scatter, and dense-prefix selection. Predictor
overhead is secondary; NVMe remains 80-87% of latency.

WHAT DID NOT WORK:
At low caps, active-set deltas become large and I/O dominates. The method
does not reach 10-20 tok/s. Platform-specific mapped staging/coherence and
GPU kernels do not transfer directly to CPU.

LIMITATIONS:
Mistral/Llama-like model, Jetson GPU/unified-memory hardware, no dense Qwen3.8
conversion, no <8 GB x86 result. The paper's handling of down matrices should
be replicated exactly before using its bytes/neuron calculation.

ASSUMPTIONS:
Activation masks persist across tokens; centroids generalize; contiguous
neuron records and O_DIRECT queues outperform page cache; a dense prefix can
fit.

TRANSFER TO QWEN3.8-27B:
This is the strongest direct system template: centroid or low-rank mask
predictor, one early predictor, delta reads, fixed slots, coalesced ranges,
O_DIRECT/io_uring experiment, and dense prefix. Qwen requires a new gated
contribution threshold, 64-layer/hybrid mapping and x86 CPU kernels. Its
reported bytes/token give a realistic warning: even excellent reuse may not
meet 10-20 tok/s under 8 GB.

TRANSFER TO LLAMA.CPP:
The layout/scheduler ideas transfer conceptually. Linux io_uring/O_DIRECT can
be tested, but C++ CPU staging and quantized deinterleave kernels replace
CUDA/Jetson paths. Exact read histograms must be added.

WHAT WE SHOULD COPY:
[PRIOR ART] Delta sets; fixed slot map; mask clustering; one lookahead
predictor; dense prefix; sorted range coalescing; O_DIRECT microbenchmarks;
read bytes/token and latency fractions.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Jetson throughput, predictor size, activation thresholds,
or GPU staging as Qwen/x86 guarantees. Do not claim delta prefetch itself as
novel.

OPEN QUESTIONS:
Will Qwen3.8 gated group masks persist 82-85% across decode? Can 4-bit group
records reduce the 24.5 KiB/neuron equivalent enough? Can CPU execution and
NVMe overlap without a GPU scheduler? What dense-prefix size leaves useful
cache under 8 GB?

[S19] SWAP-MOE

TITLE: Swap-MoE: On-Demand SSD Loading for Inference of Massive MoE Models in Low-RAM Environments
AUTHORS: ek15072809 repository author
YEAR: 2026
VENUE: Open-source llama.cpp patch and technical report
URL: https://github.com/ek15072809/Swap-MoE
CODE: Single patch `llama.cpp-expert-streaming.patch`, targeting llama.cpp
      commit f5e85d43a (2026-08-28)
RELEVANCE: very high for implementation prior art

PROBLEM:
Make very large native MoE GGUF models run on a 16 GB RAM CPU-only PC when
the routed expert tensors alone exceed physical memory.

KEY IDEA:
Leave routed expert tensors mmap-backed on SSD, prevent the normal loader from
touching them, and let OS demand paging fetch selected experts. Add optional
per-layer keep-recent eviction, expert-fixation windows, and previous-pass
expert prefetch.

ARCHITECTURE:
The patch recognizes `blk.<layer>.ffn_gate_exps.weight`, `ffn_up_exps`,
`ffn_down_exps` and fused variants, while keeping the router, shared experts
and tiny scale tensors resident. It applies Linux `madvise` to make routed
pages nonresident after mapping. It targets CPU-only llama.cpp and standard
native MoE routing; it is not a dense-to-sparse converter.

ALGORITHM:
Streaming leaves selected expert pages to page faults. `--expert-keep-recent N`
tracks a per-layer LRU and calls `MADV_DONTNEED`/Windows equivalent outside
the window. `--expert-fixation N` repeats the first route for N passes to make
page-cache reuse explicit, at a quality cost. `--expert-prefetch` uses the
previous forward pass's expert IDs and `madvise(WILLNEED)` in a background
thread. Fixation is inserted as a graph node so graph shape remains stable.

IMPORTANT EQUATIONS:
The useful accounting is direct:
`resident = nonexpert + shared + router + keep_recent experts`;
`fresh SSD bytes/token = sum(selected expert regions not in page cache)`.
There is no learned predictor equation; previous-route reuse is the predictor.

TRAINING REQUIRED:
None for streaming/prefetch. Fixation changes the route and can harm quality.

INFERENCE MECHANISM:
CPU-only llama.cpp; mmap/demand paging or explicit page hints. The normal
loader's validation/upload touches all tensors, so the patch changes that
specific path. This is a critical distinction from merely passing `--mmap`.

MEMORY BEHAVIOR:
README benchmark: 13th-generation Intel Core i7, 16 GB RAM, NVMe, CPU-only.
Routed weights are outside the resident set until selected. Explicit LRU
eviction is available for a hard RAM cap, although OS page-cache management
was faster in the author's measurements.

I/O BEHAVIOR:
Page faults are layout-blind at page granularity. Expert fixation reuses the
same pages but changes routing. Prefetch warms the next pass and carries no
intentional route-quality cost. It does not coalesce dense-derived groups.

THROUGHPUT RESULTS:
At decode token 400, reported CPU-only values include Qwen3.5-35B-A3B Q4_K_M
7.01 tok/s streaming, 7.28 with fixation N=2, and 5.89 with keep-recent 12;
Qwen3.5-122B-A10B Q2_K about 2.00 streaming; DeepSeek-V4-Flash 0.39/0.55
streaming/prefetch; Qwen3.8-Flash-Next IQ1_M 0.63. These are instantaneous
decode values on one machine, not the dense Qwen3.8 target.

QUALITY RESULTS:
Streaming/prefetch are intended to preserve exact routing. Fixation can cause
severe repetitive/incoherent output on larger or low-bit models despite a
higher raw tok/s number. It is not a free temporal-locality optimization.

HARDWARE:
13th-gen Intel Core i7, 16 GB physical RAM, NVMe SSD, CPU-only. This is the
closest public x86 implementation result found, though it uses native MoE.

WHAT ACTUALLY CAUSED THE SPEEDUP:
Skipping initial expert reads, demand paging only routed tensors, page-cache
reuse and prior-pass prefetch. The high-level mechanism is directly relevant;
the measured bytes are not published as a clean per-token table.

WHAT DID NOT WORK:
Explicit eviction often ran slower than the OS page cache. Fixation trades
quality for I/O and fails on input-token/hash routing. Qwen3.8-Flash-Next at
0.63 tok/s demonstrates that running does not imply the desired rate.

LIMITATIONS:
Native MoE only; page-fault granularity; no dense-to-group conversion; no
8 GB target; patch must be ported as llama.cpp changes. The README says
Qwen3.8-Flash-Next is a separate qwen4exp MoE model, not the Qwen3.8-27B
dense checkpoint in this notebook.

ASSUMPTIONS:
The OS page cache can manage selected expert pages; selected expert tensors
are already laid out in standard GGUF tensors; native routing is accurate.

TRANSFER TO QWEN3.8-27B:
Copy the loader bypass, resident/nonresident tensor classification, optional
hard-cap eviction and previous-pass prefetch experiment. Do not use page
faults as the final dense-derived group layout; explicit aligned ranges and
delta reads should be compared against it.

TRANSFER TO LLAMA.CPP:
This is direct implementation prior art. A dense-derived sparse MLP would
need new tensor naming/metadata and an operator, but the loader and memory
budget lessons apply.

WHAT WE SHOULD COPY:
[PRIOR ART] Keep router/shared/non-routed tensors resident; prevent startup
touches; compare OS page cache with explicit eviction; benchmark prefetch
without route mutation; test CPU-only first.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Expert fixation as a general solution, page-fault I/O as
the only layout, or native MoE throughput as dense Qwen evidence.

OPEN QUESTIONS:
How does explicit group-range `pread` compare with mmap page faults for Qwen
gated groups? Can a dense-derived tensor family use the same loader bypass?

[S20] LLAMA.CPP DISK-OFFLOAD RFC AND X86/CUDA FIELD REPORT

TITLE: RFC+PoC: MoE offload to disk with on-demand paging; plus independent
       expert-streaming-win measurements
AUTHORS: llama.cpp discussion participants, including kisasexypantera94 and
         koren1712
YEAR: 2026
VENUE: llama.cpp Discussion #23324 / implementation field report
URL: https://github.com/ggml-org/llama.cpp/discussions/23324
     https://github.com/koren1712/llama.cpp/tree/expert-streaming-win
CODE: Prototype compact pool/sidecar and Windows/CUDA branch
RELEVANCE: very high

PROBLEM:
Avoid wiring all native MoE expert weights in Metal/GPU memory by loading only
selected experts into a compact pool, with an explicit CPU sidecar.

ARCHITECTURE:
Each MoE layer has a compact N-slot expert pool, a route-ID sidecar and an
asynchronous storage path. The M1 prototype is Metal/CPU; the linked field
report is Windows/CUDA with an NVMe tier.

KEY IDEA:
Each MoE layer has N slots. A GPU/Metal interceptor publishes selected expert
IDs; a CPU sidecar resolves IDs with an LRU, loads missing GGUF regions using
`pread`, updates slot IDs and signals a shared event. The main MoE matmul runs
against the compact pool. The discussion reports Qwen3-30B-A3B Q6_K at 13
tok/s on M1 Pro 16 GB with 8-80 slots, with 12 tok/s at 8 slots.

ALGORITHM:
The slot constraint is `ub * n_expert_used <= n_slots`. The prototype requires
`--no-mmap` to avoid allocating all expert tensors and `--no-warmup` because
the default 2048-token warmup can OOM. Replies report simple LRU; layer-wise
streaming with readahead is an alternative. The Windows/CUDA report measured
async read pools, in-op overlap, pinned early blocks and a zero-copy slab.

IMPORTANT EQUATIONS:
The independent report measured 2.98 GB/s sequential NVMe and 16 MiB expert
reads at about 2.80 GB/s during live generation versus 377 MB/s mmap paging.
On a GLM-4.5-Air Q4_K_M 73.5 GB model, baseline mmap was 0.43 tok/s,
persistent async read 0.66, overlap 0.68, and four early VRAM blocks 0.75.
A 16 GiB slab reduced total reads from 132 to 76 GB but was slower from copy/
eviction overhead; 24 GiB of RAM tier on a 32 GB machine collapsed to 0.12.
The report calls out 4.13 GB/token pure streaming and 3.82 GB/token with
four VRAM blocks as the bytes/token wall.

TRAINING REQUIRED: None for storage prototype; native MoE route is retained.
INFERENCE MECHANISM: Compact fixed slots, sidecar `pread`, synchronization.
MEMORY BEHAVIOR: Explicit slots make a hard cap possible; cache metadata and
warmup allocation matter.
I/O BEHAVIOR: Large explicit reads outperform page-fault paging in the report;
copy/eviction can outweigh fewer SSD bytes.
THROUGHPUT RESULTS: 12-13 tok/s M1 prototype; 0.43-0.75 tok/s Windows/CUDA
field report for a much larger GLM model.
QUALITY RESULTS: Exact inference claimed for the M1 prototype; no dense-derived
quality result.
HARDWARE: M1/M3 Apple and i7-8700K + RTX4080 + PCIe3 NVMe in the field report.

WHAT ACTUALLY CAUSED THE SPEEDUP: Fixed slots, direct large reads, overlap and
not touching all expert tensors at startup.
WHAT DID NOT WORK: A large RAM slab can be slower despite less I/O; memory
pressure can collapse throughput; mmap page faults can sustain only 377 MB/s
in the reported live pattern.

LIMITATIONS:
Discussion/field-report numbers are not peer-reviewed and use native MoE,
different hardware and incomplete methodology. The M1 prototype uses Metal;
the x86 report uses GPU compute and does not establish CPU-only Qwen3.8.

ASSUMPTIONS:
Expert tensors can be read contiguously; compact slots fit the backend;
sidecar synchronization is cheaper than page faults.

TRANSFER TO QWEN3.8-27B:
This is an important baseline for the future storage experiment: compare
explicit aligned `pread`/io_uring group reads against mmap page faults and
measure copy/eviction cost. The reported 3.82-4.13 GB/token figures reinforce
that bytes/token, not model file size, decides throughput.

TRANSFER TO LLAMA.CPP:
The compact-pool integration point, `--no-mmap`/warmup caveat, and sidecar
request protocol are useful prior art. For CPU-only dense-derived groups,
replace GPU event synchronization with a bounded asynchronous read queue.

WHAT WE SHOULD COPY:
[PRIOR ART] Fixed slot pool; explicit `pread`/large-range baseline; direct
comparison to mmap; startup/warmup audit; bytes/token wall analysis.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Assume Metal shared events or GPU graph nodes transfer to
x86 CPU; assume fewer bytes automatically means faster execution.

OPEN QUESTIONS:
Can Qwen3.8 group records be read at 16 MiB-sized coalesced ranges without
overfetching most omitted groups? What is the CPU-only crossover between
copy/dequant and page-fault traffic?

YEAR: 2026
VENUE: arXiv preprint
URL: https://arxiv.org/abs/2601.17063
CODE: No public implementation verified during this pass.

PROBLEM:
LRU/LFU expert caches evict experts that remain hot for several future steps,
causing SSD loading to dominate decode under tight RAM.

KEY IDEA:
Train a lightweight eviction model using recency and frequency signals and
oracle/Belady-derived labels. Load routed experts once per inference iteration
and replace cache entries asynchronously while loading.

ARCHITECTURE:
SSD-backed expert files, limited DRAM, GPU/edge execution and a learned cache
policy. The system is native MoE, not dense-to-sparse conversion.

ALGORITHM:
For each candidate expert, normalize recency/frequency features and predict
which entries to evict. During decode, expert loading can be about 3 ms while
FFN computation is about 158 microseconds in the paper's comparison, so cache
policy computation can be overlapped and is justified by hit rate.

IMPORTANT EQUATIONS:
The cache model consumes recency `r_t` and frequency `f_t`; labels identify
the least useful expert under an oracle future reference trace. The practical
objective is maximize hit rate / minimize `fresh SSD bytes = misses * expert
bytes`.

TRAINING REQUIRED:
Offline cache-policy training from routing traces; no model fine-tuning.
INFERENCE MECHANISM: Prefetch/load routed experts, async replacement.
MEMORY BEHAVIOR: Evaluation deliberately leaves about 1 GB system DRAM free.
I/O BEHAVIOR: Cache hit rate is the primary I/O lever; expert loading is over
70% of total decode time in the reported setup.

THROUGHPUT RESULTS:
On a user-grade desktop, FlashMoE reports up to 2.6x over existing systems;
its Qwen3-30B-A3B comparison improves about 7% over LRU. The abstract reports
up to 51% cache-hit improvement over LRU/LFU; exact hardware/model tables must
be retained when comparing.

QUALITY RESULTS: Native MoE quality is preserved; no route mutation.
HARDWARE: Desktop/edge system with approximately 1 GB available DRAM in the
stress evaluation; not Qwen3.8 dense or CPU-only proof.

WHAT ACTUALLY CAUSED THE SPEEDUP: Learned cache replacement and asynchronous
overlap, not fewer model FLOPs.
WHAT DID NOT WORK: Pure LRU can evict experts that remain hot for 4-5 steps;
cache misses dominate. The paper does not solve group layout or predictor
false negatives.

LIMITATIONS: Native MoE, cache policy needs routing traces, no dense Qwen3.8,
no exact x86 CPU target or 8 GB total RSS result.
ASSUMPTIONS: Recency/frequency predict future expert reuse and cache policy
overhead is hideable.

TRANSFER TO QWEN3.8-27B:
Use learned eviction only after basic LRU/global-cache traces are collected.
For dense-derived groups, recency/frequency should be augmented with group
contribution and predicted delta cost; a cache model cannot repair bad route
prediction.

TRANSFER TO LLAMA.CPP:
Potentially implement as an optional cache policy; first expose trace/replay
interfaces rather than hard-coding a learned policy.

WHAT WE SHOULD COPY:
[PRIOR ART] Recency+frequency replacement, oracle replay evaluation, async
policy execution, and the observation that cache policy matters after SSD
loading dominates.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Claim a better cache policy solves the dense-derived group
selection or resident-floor problem.

OPEN QUESTIONS:
Does a learned cache policy beat LRU for Qwen3.8 group deltas under one stream,
or does fixed slot/delta ordering dominate? What is the memory/CPU cost of the
policy under 8 GB?

[S22] HOBBIT

TITLE: HOBBIT: A Mixed Precision Expert Offloading System for Fast MoE Inference
AUTHORS: Peng Tang, Jiacheng Liu, Xiaofeng Hou, Yifei Pu, Jing Wang,
         Pheng-Ann Heng, Chao Li and Minyi Guo
YEAR: 2024
VENUE: arXiv preprint
URL: https://arxiv.org/abs/2411.01433
CODE: Implemented on top of llama.cpp; public paper was inspected.
RELEVANCE: high

PROBLEM:
Expert loading dominates MoE offloading, while skipping cache-miss experts
harms quality.

KEY IDEA:
Replace less critical cache-miss experts with lower-precision versions,
prefetch next-layer experts, and use a multidimensional sequence-aware cache.
Mixed precision is used to make wrong prefetch/cache choices less expensive.

ARCHITECTURE:
Dynamic expert loader, adaptive expert predictor and multidimensional cache
manager. It assumes non-expert weights and a hot expert cache in faster memory;
cold experts are CPU/SSD-loaded.

ALGORITHM:
Expert contribution is scored from `G(x)_e E_e(x)`. For Mixtral-8x7B, one
reported setting assigns 67% experts high precision, 30% low precision and 3%
skip at thresholds T1=.6/T2=.9. Consecutive-layer gating inputs have high
cosine similarity; next-layer top-1 prediction accuracy averages about 96%.
Sequence-level cache policy accounts for high/low-precision usage and route
preferences.

IMPORTANT EQUATIONS:
The central tradeoff is not only route probability but contribution magnitude:
`importance_e(x) ~= ||G(x)_e E_e(x)||`. This is closer to our gated-group
contribution score than raw router logits.

TRAINING REQUIRED:
Cache/predictor training; no base-model conversion. Low-precision expert
variants must be prepared.
INFERENCE MECHANISM: On cache miss, score expert, enqueue read of high/low
precision variant or skip; prefetch next layers; replace cache entries.
MEMORY BEHAVIOR: GPU/CPU/SSD tiers with hot cache.
I/O BEHAVIOR: Expert loading is reported as 85.5% of time on RTX4090 and
94.5% on Jetson Orin in motivation; prefetch benefits are limited when wrong.

THROUGHPUT RESULTS:
The abstract reports up to 9.93x over prior offloading systems; evaluations
include Jetson AGX Orin and RTX4090/CPU cooperative modes. The paper does not
establish x86 CPU-only dense Qwen3.8.

QUALITY RESULTS:
Skipping 10% experts increases PPL by more than 1% in the motivation; low
precision replacement preserves quality better. The point is that approximate
wrong experts are safer than silently dropping them.

HARDWARE: RTX4090, Jetson Orin, llama.cpp and edge systems.

WHAT ACTUALLY CAUSED THE SPEEDUP: Reduced bytes/latency for lower-priority
experts, layer lookahead, and cache policy—not only predictor accuracy.
WHAT DID NOT WORK: Prefetch with low prediction accuracy can be slower because
wrong reads are expensive; expert skip causes quality loss.

LIMITATIONS: Native MoE, mixed-precision expert copies, GPU-centric kernels,
no dense-to-sparse Qwen3.8 conversion or SSD bytes/token under 8 GB.
ASSUMPTIONS: Expert importance can be scored after a miss; low-precision
variants are acceptable; adjacent-layer inputs are similar.

TRANSFER TO QWEN3.8-27B:
Borrow contribution-aware fallback: if a predicted cold group is uncertain,
load a lower-cost approximation or a conservative group rather than zero.
Use adjacent-layer similarity as a predictor feature, but test Qwen's hybrid
linear/full pattern. Mixed precision may apply to cold groups after quality
traces, though it increases disk/layout variants.

TRANSFER TO LLAMA.CPP:
Use the existing llama.cpp integration as implementation prior art for a
layer-aware loader/cache. Keep sparse-group CPU work separate from GPU-centric
precision selection.

WHAT WE SHOULD COPY:
[PRIOR ART] Contribution-based miss scoring, mixed-precision fallback,
next-layer prediction, sequence-aware cache and predictor-accuracy penalty
analysis.

WHAT WE SHOULD NOT COPY:
[PRIOR ART LIMIT] Skip experts as a quality-neutral miss policy or use GPU
latency results as CPU evidence.

OPEN QUESTIONS:
Can a cheap low-bit approximation of a missing Qwen group protect quality
under an SSD miss without increasing the resident floor? Is this better than
an exact synchronous read at 10-20 tok/s?

4. QWEN3.8-27B ARCHITECTURE MAPPING

EXACT OBSERVED CONFIGURATION

- architecture/model type: Qwen3_5ForConditionalGeneration / qwen3_5.
- hidden size: 5120.
- intermediate FFN size: 17408.
- layers: 64.
- attention: 24 query heads, 4 KV heads, head dimension 256.
- layer pattern: `full_attention_interval=4`; 48 linear/hybrid blocks and 16
  full-attention blocks in the repeating 3-linear/1-full pattern.
- linear/hybrid fields: convolution width 4, linear key heads 16 of size 128,
  linear value heads 48 of size 128, output gate swish, A_log, dt_bias,
  in_proj_a/b/qkv/z and out_proj.
- full attention fields: q/k/v/o projections, q_norm/k_norm, 24 Q heads and
  4 KV heads.
- gated activation: SiLU; MLP is `down(silu(gate(x))*up(x))`.
- vocabulary: 248320; maximum position: 262144; MTP count: 1.
- source text dtype: bfloat16.
- index metadata total BF16 size: approximately 55,562,855,904 bytes across
  18 shards, including the full released model components.

PARAMETERS / BYTES (BACK-OF-ENVELOPE)

MLP per layer:
`3 * 17408 * 5120 = 267,386,880 parameters`.
64 MLPs: approximately 17.113B parameters.
BF16 MLP per layer: approximately 534.8 MB decimal / 510 MiB.
BF16 MLP total: approximately 34.23 GB decimal.
Raw q4 MLP per layer: approximately 133.7 MB, before scales/biases.
Rough q4 MLP total with group metadata: about 9.6 GB.

Embeddings: `248320 * 5120 = 1,271,398,400` parameters.
Untied head: same order; together about 2.5428B parameters, roughly 1.3 GB
raw at q4 before quantizer metadata.

The full q4 text-only model is expected around 14-16 GB depending on tensor
quantization and metadata. This must be replaced with exact measurements once
a converter produces a target file.

HF TENSOR NAMES

- `model.language_model.embed_tokens.weight`
- `model.layers.{i}.input_layernorm.weight`
- `model.layers.{i}.post_attention_layernorm.weight`
- linear branch: `linear_attn.A_log`, `conv1d`, `dt_bias`, `in_proj_a`,
  `in_proj_b`, `in_proj_qkv`, `in_proj_z`, `norm`, `out_proj`
- MLP: `mlp.gate_proj`, `mlp.up_proj`, `mlp.down_proj`
- full attention: `self_attn.q_proj`, `k_proj`, `v_proj`, `o_proj`, `q_norm`,
  `k_norm`
- `lm_head.weight`

GGUF / LLAMA.CPP MAPPING

Current qwen35.cpp creates dense `ffn_gate`, `ffn_up`, `ffn_down` tensors and
uses a parallel SiLU FFN. The generic semantic mapping corresponds to names
like `blk.{i}.ffn_gate.weight`, `blk.{i}.ffn_up.weight` and
`blk.{i}.ffn_down.weight`, but a converted file must be inspected because
GGUF names are generated through tensor enums and mapping tables.

Candidate grouping must account for actual matrix orientation. Semantically:
gate/up have one row per intermediate neuron in HF; down has one aligned
column per intermediate neuron. In GGML layout/source shape the dimensions
are represented as `{n_embd,n_ff}` for gate/up and `{n_ff,n_embd}` for down.
The converter should move/pack all three with one permutation and record
strides/offsets explicitly.

CANDIDATE SPARSIFICATION POINTS

ATTENTION:
possible? Yes, contextual head/key/value sparsity exists in DejaVu.
risk? High for Qwen3.8: 48 linear-state blocks and 16 full-attention blocks
have different semantics; sparse state updates can create accumulated error;
KV/head misses can require recomputation. Keep dense initially.

FFN GATE PROJECTION:
possible? Yes. It is the natural early predictor/filter and can be grouped.
risk? A predictor false negative changes the final gated contribution; gate
alone is not the output importance because up and down matter.

FFN UP PROJECTION:
possible? Yes, after a gate/group mask. It must share intermediate indices.
risk? The up value is not naturally zero under SiLU; skipping small values is
an approximation, not exact ReLU sparsity.

FFN DOWN PROJECTION:
possible? Yes, select aligned down columns or down-transposed rows.
risk? Random column access and quantization layout can destroy CPU/SSD
locality; repacking is likely necessary.

WHOLE FFN EXPERTS:
possible? Yes, use MoEfication/DynaMoE-style aligned groups.
risk? Group granularity creates overfetch and group error; a conventional
router adds training/symmetry issues and does not guarantee dense quality.

NEURON CLUSTERS:
possible? Yes, likely best first unit for storage.
risk? Single-neuron records are too small for SSD; large clusters reduce
selectivity. Need contribution-aware clustering and contiguous packing.

LAYERS:
possible? Full layer paging is possible, but a 64-layer decode would read
large blocks and lose fine-grained reuse.
risk? Layer skip changes the architecture severely and leaves no good
lookahead; avoid as first path.

MTP:
possible? Could support speculative decoding.
risk? Extra resident state/compute and a second unvalidated source of error;
not useful until basic sparse decode works.

RESIDENT FLOOR ESTIMATE

Keep initially: embeddings/head, all 64 layer norms, 48 linear-attention
branches, 16 full-attention branches, routers/predictor, runtime, staging and
KV. The exact q4 floor is not yet measured. A conservative planning range is
roughly 5-7 GB for non-MLP weights plus runtime/KV depending quantization and
context. If true, an 8 GB machine leaves only approximately 1-3 GB for the
active MLP cache and staging. This is a hypothesis and must be measured from
an actual converted file.

5. CANDIDATE ARCHITECTURES
------------------------------------------------------------

All estimates below are ranges for the Qwen3.8 target, not measurements. The
model has 17.1B MLP parameters; the non-MLP resident floor is a major unknown.
Use q4 raw payload plus scales/metadata for storage estimates.

ARCHITECTURE A - MOEFICATION-STYLE GATED GROUPS

Method: Permute intermediate neurons by gated coactivation/contribution,
partition into groups (candidate 128-512 neurons), and predict top groups.

active parameters/token: approximately 10-30% of MLP if traces permit;
                         whole-model active parameter floor remains high
resident parameters:     non-MLP floor + hot groups/cache
SSD bytes/token:         roughly fresh-active-groups * 2-3 MB/group/layer;
                         target must be <=200-400 MB/token at 20-10 tok/s
random reads/token:      must be coalesced to tens/hundreds of ranges, not
                         one read per neuron
compute/token:            10-30% of MLP arithmetic plus predictor/gather;
                         dense hybrid/attention remains
predictor cost:           small MLP or SVD/group predictor; must be early
likely quality loss:      unknown for SiLU; expect measurable truncation loss
required training:        calibration; possibly distillation/fine-tuning
implementation difficulty:high; quantized down-column packing and CPU kernel

ARCHITECTURE B - DEJAVU-LIKE CONTEXTUAL GROUPS

Method: Leave dense weights semantically intact; predictor emits per-layer
group masks and sparse kernels execute selected groups.

active parameters/token: 15-30% MLP as an initial target, not a claim
resident parameters:     dense non-MLP + predictor + hot groups
SSD bytes/token:         depends on mask delta; unacceptable if each layer
                         reads full 15-30% independently
random reads/token:      poor unless ranges are sorted/coalesced
compute/token:            sparse MLP plus predictor; attention dense
predictor cost:           per-layer predictors or one early predictor
likely quality loss:      potentially low at conservative recall; gated tests
                         required
required training:        predictor labels; no model retraining initially
implementation difficulty:high CPU sparse kernel and lookahead scheduler

ARCHITECTURE C - HOT RESIDENT CORE + COLD SSD GROUPS

Method: Keep globally hot groups resident, predict context-dependent cold
groups, and stream only cold misses.

active parameters/token: 40-70% of MLP may be touched if hot coverage is good;
                         arithmetic reduction is smaller but robust
resident parameters:     non-MLP + hot core, perhaps 20-50% MLP
SSD bytes/token:         hot coverage *must* reduce misses below 200-400 MB
random reads/token:      low if hot/cold records are clustered
compute/token:            still high; likely a safer CPU path
predictor cost:           low/medium online predictor
likely quality loss:      low if all required cold groups are fetched
required training:        profiling; predictor calibration
implementation difficulty:medium-high; cache policy is central

ARCHITECTURE D - SPARSE UPCYCLED / VIRTUAL-GROUP MOE

Method: Copy dense weights into narrower/replicated experts, train a router,
and continue pretraining/distill.

active parameters/token: 25-50% of expanded capacity depending top-k/width;
                         not necessarily below original dense MLP
resident parameters:     router + hot experts + non-MLP
SSD bytes/token:         group/expert misses; layout can be sequential
random reads/token:      potentially large if many fine experts
compute/token:            controlled by top-k/width but training needed
predictor cost:           conventional router, low enough but route quality
likely quality loss:      unknown; DynaMoE shows aggressive quality loss
required training:        substantial continued training; possibly billions
implementation difficulty:high; checkpoint conversion + training + runtime

ARCHITECTURE E - SVD / GATE-FIRST SEQUENTIAL FILTER

Method: Build a low-rank predictor of gate rows, validate gate values, then
fetch/run only surviving up/down groups.

active parameters/token: predicted mask can be 30-60% sparse, realized higher
resident parameters:     non-MLP + low-rank predictor + gate metadata
SSD bytes/token:         gate prediction/data first, then surviving up/down;
                         two-stage reads may save bytes but add latency
random reads/token:      coalesce group ranges; do not read per row
compute/token:            predictor + gate + sparse up/down
predictor cost:           `r(d+D)` per layer or one shared predictor; Qwen D
                         is 17408, so this is nontrivial
likely quality loss:      unknown for SiLU; SVDP ReGLU results encouraging
required training:        calibration only initially
implementation difficulty:high; sequential CPU/SSD overlap is unresolved

ARCHITECTURE F - HYBRID RECOMMENDED HYPOTHESIS

Method: Optional static block/N:M reduction, contribution-aware Qwen gated
groups, resident hot core, one early predictor, delta prefetch, fixed staging,
and optional distillation only after trace validation.

active parameters/token: target 20-40% MLP initially; measure rather than set
resident parameters:     non-MLP floor + hot core + predictor + 0.5-2 GB cache
SSD bytes/token:         kill if sustained fresh traffic exceeds target budget;
                         aim <100-200 MB/token for 20 tok/s aspiration
random reads/token:      sorted/coalesced group ranges; target low tens
compute/token:            hybrid dense floor + 20-40% MLP + CPU bookkeeping
predictor cost:           one early group predictor, perhaps centroid/SVD
likely quality loss:      first safe target <1% local KL / small PPL shift;
                         benchmark loss unknown
required training:        calibration first; small distillation next; no
                         pretraining-from-scratch assumption
implementation difficulty:very high; only candidate aligned with question

BACK-OF-ENVELOPE STORAGE BUDGET

At 4 GB/s effective sequential storage bandwidth:
`4 GB/s / 10 token/s = 400 MB/token`.
`4 GB/s / 20 token/s = 200 MB/token`.

These are ceilings. If effective random/coalesced throughput is 1.25 GB/s,
the corresponding budgets are 125 MB/token at 10 tok/s and 62.5 MB/token at
20 tok/s. If a q4 Qwen MLP layer is roughly 150 MB and a group of 256 neurons
is about 2.0-2.5 MB including metadata, then 64 layers with 10% fresh groups
could approach 1 GB/token before delta reuse. That is impossible at 10-20
tok/s unless the active sets persist and the cache covers most data.

CONSEQUENCE: The first experiment must measure active-set overlap and bytes
after a realistic layout. An “active 10%” result without delta/read accounting
does not support the architecture.

POTENTIALLY NOVEL COMBINATION:

Post-hoc Qwen3.8 gated-FFN group conversion + Qwen hybrid-block-aware
resident-floor accounting + x86 CPU/quantized sparse kernel + GGUF-neuron/
group storage + delta prefetch/fixed slots + exact bytes/token and quality
measurements under 8 GB. The contribution would be an integrated empirical
system and its tradeoff curve, not the isolated ingredients.

DO NOT CLAIM NOVELTY FOR:

- SSD expert streaming itself;
- mmap/LRU/prefetch/fixed staging;
- contextual sparsity prediction;
- hot/cold neuron placement;
- row/column bundling;
- delta prefetch or mask persistence;
- CPU-only mmap expert streaming, explicit `pread` slot pools, learned cache
  replacement, or mixed-precision expert fallback;
- dense-to-MoE initialization;
- neuron grouping.

------------------------------------------------------------
7. FAILURE MODES
------------------------------------------------------------

- Expert/group prediction misses: false negatives either force synchronous
  random reads, use an approximation, or corrupt quality. False positives
  waste bytes and cache slots. Record both separately.
- Random I/O amplification: noncontiguous down columns or single-neuron reads
  can make “sparse” traffic slower than sequential dense reads.
- Small-read SSD collapse: align records and benchmark 4 KiB, 16 KiB, 32 KiB,
  128 KiB and multi-range requests on the actual drive.
- Cache thrashing: a global cache can help cross-layer reuse but one hot
  sequence can evict another layer's working set. Track per-layer and global
  hit rates.
- Activation distribution shifts: prompt calibration may not represent long
  autoregressive decode, code, multilingual prompts or rare reasoning tokens.
- Activation shift after sparsification: a small MLP error changes the next
  layer's routing/active set, so local error can compound.
- Router collapse/expert symmetry: copied experts remain identical without
  enough training; router loss can collapse to one group.
- Quality loss from SiLU approximation: unlike ReLU, omitted negative/small
  values are not exact zeros. Down projection norms alone are insufficient.
- Dense floor dominance: 48 linear-attention blocks, 16 full-attention blocks,
  embeddings, norms and output head can dominate after MLP pruning.
- Output embedding/head dominance: the untied 1.27B-parameter head is a
  resident compute/memory cost and may erase the expected speedup.
- Quantization interactions: group scales/biases, dequantization and row/column
  repacking can alter contribution rankings and add metadata overhead.
- CPU sparse-kernel overhead: gathers, sorting, branchy loops and small GEMMs
  can cost more than skipped multiplies; BLAS dense kernels may win at modest
  sparsity.
- Bookkeeping overhead: route prediction, slot maps, locks, futures and
  synchronization can dominate one-token decode.
- Page-cache interference: mmap can evict resident model/KV pages; `WILLNEED`
  is advisory, and accidental page faults can serialize execution.
- Linux readahead mismatch: sequential readahead can help ranges or read too
  much; O_DIRECT may be necessary but increases alignment/implementation work.
- OS demand paging is layout-blind and can sustain much less live throughput
  than explicit large reads. Swap-MoE/RFC evidence requires a direct mmap vs
  `pread` comparison, not an assumption that one always wins.
- Explicit eviction can cost more memcpy/syscall time than it saves in SSD
  reads; a hard RSS cap and peak throughput may require different policies.
- Route fixation can turn high apparent tok/s into unusable output. Temporal
  reuse must be measured with quality, not imposed by freezing the route.
- mmap accidentally becoming resident: virtual address size is not RAM use;
  measure RSS/PSS and major faults, not mapped bytes.
- SSD endurance and energy: high reads/token can consume energy and device
  lifetime even if latency is overlapped. See [S15].
- Preprocessing/layout cost: creating grouped q4 records, changing down
  orientation, storing indexes and validating tensor alignment can be a large
  conversion project.
- Predictor storage: NeuroPrefetcher shows a predictor can consume hundreds
  of MB; under 8 GB this is material.
- Prefill/decode mismatch: a full-layer prefill path may be optimal while
  token decode needs delta groups. Do not use prompt throughput as decode.
- KV-cache growth: long context consumes RAM and reduces active group cache.
- Hybrid-state error: sparse MLP errors enter linear-attention recurrent state
  and may persist longer than in ordinary full-attention blocks.
- Tooling mismatch: MLX, CUDA, CANN, Android and Jetson synchronization do
  not prove x86/llama.cpp behavior.
- Token capacity/dropping: Switch-style overflow is unacceptable unless a
  dense/exact fallback prevents silent quality loss.

[PRIOR ART] Build an activation-trace tool that records per-layer gate, up,
down contribution, selected group IDs, group byte ranges, active-set overlap,
and local/full-model output error. Inspired by MoEfication [S02], SVDP [S14]
and NeuroPrefetcher [S18].

[PRIOR ART] Preserve the same intermediate permutation across gate/up/down and

and NeuroPrefetcher [S18].

[OUR HYPOTHESIS] Use contribution score
`q_i=|silu(gate_i)*up_i|^2 * ||down[:,i]||^2` and a group score that includes
within-group contribution correlation. This is a Qwen-specific extension;
validate against exact output error.

[PRIOR ART] Keep a global bounded LRU plus a separate prefetch buffer and
fixed staging slots. From Edge0 [S01].

[PRIOR ART] Use one early predictor with a one-layer/multi-layer horizon and
delta sets rather than per-layer-late prediction. From Edge0 [S01], DejaVu
[S07] and NeuroPrefetcher [S18].

[OUR HYPOTHESIS] Use a Qwen-specific low-rank/SVD gate predictor as a training-
light alternative, with per-group damage-aware thresholds and optional
gate-first reads. Inspired by SVDP [S14], but Qwen uses SiLU and needs new
validation.

[PRIOR ART] Store gate/up/down group data in sorted contiguous ranges; consider
O_DIRECT/io_uring, aligned staging and fixed slot maps. From Flash [S03] and
NeuroPrefetcher [S18].

[OUR HYPOTHESIS] For llama.cpp, introduce a separate sparse-FFN tensor family
and operator rather than making ordinary GGUF mmap tensors page-fault into the
working set. Store an index table with layer/group offsets, quantization
metadata, and aligned gate/up/down strides.

[PRIOR ART] Retain globally hot groups in RAM and stream context-dependent
cold groups. From PowerInfer [S08] and PowerInfer-2 [S04].

[MODIFICATION] Make the hot score a combination of global frequency, expected
SSD read cost, contribution norm and predicted next-token probability, rather
than frequency alone.

[PRIOR ART] Use full-layer reads during prefill and sparse/delta reads during
decode. From Edge0 [S01].

[MODIFICATION] Keep all Qwen3.8 attention/linear tensors on the dense path for
the first experiment; add attention sparsity only after MLP-only traces pass.

[OUR HYPOTHESIS] Optional SparseGPT-style static block/N:M reduction can lower
the SSD pool before contextual selection, but only if applied consistently to
the gated groups and measured separately from dynamic sparsity.

[PRIOR ART] Record exact cache hits, wasted prefetch, reads/token, range-size
histogram, major faults, queue depth, overlap and stall time. Edge0 exposes
several counters; Flash/NeuroPrefetcher show why these measurements matter.

[PRIOR ART] Benchmark two storage paths before choosing one: OS mmap/page
faults with `madvise`, and explicit aligned `pread`/io_uring into fixed slots.
Swap-MoE [S19] and the llama.cpp RFC/field report [S20] show that their
relative performance is hardware/layout dependent.

[PRIOR ART] Evaluate learned cache replacement only after an LRU trace exists.
FlashMoE [S21] uses recency/frequency and oracle replay; HOBBIT [S22] adds

[MODIFICATION] Add a quality-aware emergency path inspired by HOBBIT [S22]:
when a predicted group is uncertain, choose exact synchronous read, a cheaper
low-bit approximation, or a conservative resident group. Never silently drop
the group in quality measurements.

[MODIFICATION] Define emergency miss policy: first try a bounded synchronous
read; if latency exceeds a threshold, use a quality-preserving dense fallback

[OUR HYPOTHESIS] Distill the sparse model to the dense Qwen3.8 logits after
the trace chooses a target group budget. Only then consider a router or
virtual-group upcycling. This avoids spending training effort on an impossible
SSD byte budget.

9. EXPERIMENTS WE MUST RUN

EXPERIMENT 1 - GATED QWEN ACTIVE-SET / ERROR TRACE (FIRST IMPLEMENTATION)

hypothesis:
Qwen3.8 gated MLP contributions can be grouped so that a substantial fraction
of MLP rows can be omitted per token, with high token-to-token overlap and a
storage traffic budget compatible with a future 10-20 tok/s design.

model:
Qwen3.8-27B text-only checkpoint if feasible. If 27B cannot fit for tracing,
use a smaller Qwen3.5/Qwen-family gated model only as a pipeline proxy and
label all results as proxy. Trace full dense outputs first; do not modify
weights or begin a sparse implementation.

hardware:
Available Linux/x86 machine; record CPU, RAM, NVMe model, filesystem,
quantization, threads. A GPU is acceptable for trace generation but the
trace must be replayable against x86 storage assumptions.

metric:
Per-layer and whole-model next-token KL/logit error; MLP output relative L2;
active fraction at multiple thresholds; group truncation error; gate/up/down
contribution; Jaccard overlap across adjacent tokens; contiguous range count;
fresh group bytes/token under candidate group sizes 64/128/256/512; prompt vs
decode split; CPU trace time.

success threshold:
At least one operating point with >=50% MLP activity omitted (or a clearly
measured lower bound for unmodified SiLU), <=1% local calibration perplexity
or small agreed KL increase, >=80% adjacent active-set persistence, and
estimated coalesced fresh reads <=200-400 MB/token before overlap optimism.

kill threshold:
No point below 30% omitted activity at acceptable error; adjacent overlap
below 60%; or every acceptable-quality point requires >400 MB/token at an
effective 4 GB/s device. If the resident floor alone exceeds 8 GB, stop the
8 GB objective or reduce model scope before building a runtime.

EXPERIMENT 2 - STORAGE LAYOUT MICROBENCHMARK

hypothesis:
Aligned group records and sorted range reads make the selected Qwen groups
fast enough; per-neuron/page-fault access does not.

model:
Synthetic records with exact Qwen3.8 q4 dimensions plus a small real converted
layer. Compare group 64/128/256/512 and gate+up+down layouts.

hardware:
Target Linux/x86 NVMe; report filesystem, direct/buffered I/O, queue depth,
threads, read alignment and thermals.

metric:
MiB/s, p50/p95/p99 read latency, IOPS, CPU copy/dequant time, ranges/request,
bytes overfetched, queue depth, read amplification and energy if available.

baseline variants:
Include ordinary mmap/page-fault reads, Swap-MoE-style `madvise` streaming,
explicit `pread`/io_uring, and the compact fixed-slot approach from the
llama.cpp RFC [S19] [S20]. This comparison is required before selecting a
GGUF storage format.

success threshold:
Sustained candidate delta reads at >=50% of the device's realistic sequential
bandwidth with bounded p99; group reads materially beat one-neuron/page reads.

kill threshold:
Small/range reads remain below the bytes/token budget even with full overlap,
or CPU dequant/gather dominates the dense baseline.

EXPERIMENT 3 - EXACT REPLAY CACHE/PREFETCH SIMULATOR

hypothesis:
Edge0/NeuroPrefetcher-style global cache, fixed slots and delta prefetch can
keep cold reads within budget using the actual Qwen trace.

model: Experiment 1 traces; no model execution needed.
hardware: Parameterized by measured NVMe/CPU results; then real machine.
metric: cache hit/miss, wasted prefetch, fresh bytes/token, ranges/token,
lookahead misses, slot churn, queue occupancy, hypothetical stall time.
success threshold: >=80% active-set reuse, >=90% predicted-group recall,
fresh bytes within target at p95, no pathological per-layer thrashing.
kill threshold: p95/prompt shifts cause >400 MB/token, predictor recall below
99% for the groups that matter, or cache needs more RAM than available.

EXPERIMENT 4 - CPU SPARSE FFN VS DENSE BASELINE

hypothesis:
At the trace-selected group sizes, CPU sparse execution plus predictor/gather
is faster than dense q4 FFN, not just fewer FLOPs.

model: one or several Qwen3.8 MLP layers, then full text decode.
hardware: target x86 CPU, one thread count sweep, RAM under target cap.
metric: layer time, decode tok/s, predictor time, gather/dequant time, branch
misses/cache misses, dense-vs-sparse crossover by active fraction.
success threshold: measured layer and end-to-end speedup at the selected point;
initially require >=1.2x end-to-end before any SSD complexity.
kill threshold: dense q4 wins at all acceptable sparsity points or sparse
bookkeeping consumes the expected savings.

EXPERIMENT 5 - QUALITY RECOVERY

hypothesis:
Small calibration/distillation/fine-tuning recovers most of the gated group
truncation loss without changing the bytes budget.

model: Qwen3.8 target or proxy, group layout from Experiment 1.
hardware: available training/inference hardware; record tokens and time.
metric: calibration KL/PPL, WikiText2, HellaSwag and selected math/code tasks;
long-context recurrent/hybrid-state drift; active bytes unchanged.
success threshold: <=1-2% benchmark degradation at the selected IO budget,
with a reproducible finite training budget.
kill threshold: quality recovery requires full pretraining-scale data or
increases active bytes enough to invalidate storage.

EXPERIMENT 6 - END-TO-END STORAGE-RESIDENT DECODE

hypothesis:
The integrated design reaches useful tokens/s under 8 GB without silent
quality fallback.

model: final chosen Qwen3.8 sparse representation.
hardware: Linux/x86, <=8 GB RSS cap, target NVMe, single stream, context and
decode lengths reported separately.

metric: tok/s prefill/decode, p50/p95 token latency, RSS/PSS, major faults,
bytes read/token, read ranges, SSD utilization, CPU utilization, cache/predictor
stats, benchmark quality.

success threshold:
At least 10 tok/s decode with <=8 GB RSS would meet the ambitious target; a
lower reproducible point with a clear bottleneck is still scientifically useful.

kill threshold:
Below 5 tok/s at the most favorable safe quality point, >8 GB RSS, or
quality fallback/misses that cannot be bounded. Do not continue to optimize a
design that fails the first three experiments.

11.1. RECOMMENDATION AND SCOPE

The best framing is constrained capability transfer: use the dense model as
a teacher, and learn a deployment representation whose frequently executed
computation fits the laptop. Preserve task performance, not the teacher's
neuron identities, layer count, or parameter count. The important separation
is between reusable stored capacity and the computation required to use it.

My strongest research bet is a compact, resident, quantized language model
with trainable, context-addressed neural memory on SSD. The memory supplies
small vectors or low-dimensional rank-one transformations, rather than
multi-megabyte FFN experts. Distill Qwen3.8-27B into BOTH the resident model
and this memory. Keep a capable dense path in the small model; do not expect
lookups alone to implement general reasoning.

This is principally a PKM/Memory+/PEER/UltraMem direction [S23-S27], with a
teacher-transfer objective. It is not a claim to have invented neural
memory. Token-addressed memory and offline teacher representations
[S28-S32] are important alternatives and controls, but I would not make
short n-gram lookup the only route by which the model accesses its capacity.

A plausible first deployment envelope is approximately 3.4 GB application
memory, 4.2B resident backbone parameters, approximately 8.6 billion
multiply/add-equivalent operations per token before context-dependent state
work, and 4 MiB of cold SSD reads per token in the example below. Around
5-10 decode tokens/s is a plausible engineering target on a sufficiently
capable laptop CPU; it is NOT a measurement or a guarantee. The 2 GB version
requires a smaller or natively lower-bit backbone and has a substantially
less certain capability frontier.

The decisive unknown is whether this representation can retain enough
capability after feasible training. No examined source demonstrates the full
combination of Qwen3.8-27B capability retention, <=4 GB total application
memory, and interactive x86 CPU inference. Existing papers establish useful
parts, not the desired endpoint. An ordinary well-distilled small dense
model may still beat the proposed system.

The recommendation supersedes the architecture preference and first
experiment in Sections 5 and 9 for the NEW <=4 GB objective. Earlier
sections are retained as the historical research checkpoint. No architecture
or training pipeline is implemented by this appendix.

Assumptions and units:
- Text-only, one user and one decoding stream; no GPU/NPU at deployment.
- Initial supported context: 4096 tokens. Longer context is a separate
  operating point, not free because the checkpoint advertises it.
- GB means 10^9 bytes; GiB means 2^30. MB and MiB follow the same convention.
- RAM includes resident weights, recurrent/KV state, retrieval indexes,
  cache, read buffers, scratch, runtime, and an allocation margin. All model
  file-cache pages count, whether or not they appear as anonymous RSS.
- A 4 GB APPLICATION budget differs from a laptop with 4 GB PHYSICAL RAM.
  The latter needs an explicit OS/application reserve. Both cases are
  considered below.
- Training and teacher evaluation can use larger machines. Laptop inference
  constraints are not a claim that teacher distillation fits on that laptop.
- Proposed practical gates: >=5 sustained decode tokens/s, p95 token
  latency <=300 ms, and <=10 s time to first token for a 256-token prompt.
  These are research acceptance criteria, not inferred user requirements.
  Also report 10 tokens/s as the stronger target and long-prompt latency.

11.2. WHAT IS ACTUALLY CONSTRAINED

A dense checkpoint is a program implementing a conditional distribution.
Its abilities are distributed across representations: language fluency,
world knowledge, compositional operations, in-context adaptation, reasoning,
instruction following, and calibration. There is no known theorem assigning
each of these to a disjoint set of weights. In particular, "FFN = facts,
attention = reasoning" is too simple to justify a design.

Nevertheless, the deployment cost depends on how information is accessed.
Reading a vector of already learned features can cost kilobytes. Reading a
matrix that computes those features can cost megabytes. A learned
representation that changes this unit of access is more consequential here
than optimizing the cache for the original matrices.

A useful objective is:

  maximize task capability Q on held-out deployment distributions
  subject to:
    peak charged RAM <= M,
    sustained and tail latency <= chosen budgets,
    disk capacity <= a stated practical allowance,
    CPU-only execution,
    a finite, reported training/data budget.

For a conventional execution path, necessary resource bounds include:

  token time >= max(B_DRAM / bandwidth_DRAM,
                    B_SSD / bandwidth_SSD,
                    operations / effective_compute_rate).

This is an optimistic lower bound, not an additive runtime prediction.
Dependencies, sequential I/O waves, dequantization, top-k selection, cache
management, and OS scheduling add time. Rates must be sustained rates for
the ACTUAL kernels and read patterns; advertising peak CPU FLOPs and SSD
sequential bandwidth is insufficient.

If R reads can run only q at a time and take service time l, a simple
sensitivity model is ceil(R/q)*l. Apply it separately at each dependent
layer. It is not a universal SSD law: contention, read merging and tail
latency change the result. It does expose why bytes alone are insufficient.

For the final capability evaluation, report separate domain scores and
absolute point losses. On multiple-choice tasks, also report
(Q_student - chance)/(Q_teacher - chance), where meaningful. Raw percentage
retention can hide a large fraction of useful capability lost above chance.
Report executable code pass rates, exact math answers, instruction
compliance and long-context behavior separately. Do not average unlike
metrics into an unexplained "92% intelligence" claim.

Use two comparisons:
1. Retention relative to the dense teacher, evaluated with the same tools,
   prompts, sampling and output-budget policy.
2. Improvement over the strongest fully resident model at the SAME memory
   and wall-clock budget, including matched distillation.

Evaluate both fixed generated-token budgets and fixed time-to-answer.
A small model that needs four times as many reasoning tokens can lose its
latency advantage despite a high displayed decode rate.

11.3. RE-DERIVING THE ORIGINAL MODEL'S FLOOR

The current primary configuration agrees with the notebook's main
dimensions [S16]. The following are analytical counts of the large text
matrices, not tensor-header measurements of a converted checkpoint.

Using the output gate in full attention, the dominant matrices are:

  MLP:
    64 * 3 * 5120 * 17408                 = 17.11276032B parameters

  Linear blocks:
    48 * 5120 * (10240 + 6144 + 6144 + 96)
                                             = 5.56007424B
    Terms: qkv, z, output, and the two small a/b projections.

  Full-attention blocks:
    16 * 5120 * (12288 + 1024 + 1024 + 6144)
                                             = 1.67772160B
    Terms: gated query projection, key, value, output.

  Separate embedding and output head:
    2 * 248320 * 5120                       = 2.54279680B

  Dominant non-MLP matrices                 = 9.78059264B

At an ASSUMED average 4.5 stored bits/weight, including quantizer overhead,
the non-MLP matrices alone occupy 5.5016 GB. Norms, convolution, recurrent
state, KV, runtime, predictors and buffers are additional. This substantiates
the earlier floor estimate and rules out that particular resident partition
at <=4 GB. Even deleting every FFN would not make it fit.

A 4096-token FP16 full-attention KV cache is approximately:

  2 * 16 layers * 4096 * 4 KV heads * 256 * 2 bytes
    = 268.4 MB.

FP32 recurrent matrices alone are approximately:

  48 layers * 48 value heads * 128 * 128 * 4
    = 151.0 MB,

before convolution state and implementation-dependent extras. "Linear
attention" does not mean zero state or zero projection cost.

Several tempting arithmetic shortcuts fail:
- At exactly 2 bits/weight, 27B weights still require 6.75 GB before metadata.
- A fixed-rate ternary code at log2(3) bits/weight needs 5.349 GB for 27B.
  Skewed ternary distributions might entropy-code smaller; this number is
  not an information-theoretic lower bound on all trained models.
- Exactly one bit for every one of 27B weights is 3.375 GB before scales,
  embeddings requiring other precision, state, and runtime. Binary
  post-training conversion with retained capability is unestablished here.
- A 3 GB weight allowance corresponds to only 0.889 bits per ORIGINAL 27B
  parameter if every parameter is retained. That is a requirement imposed
  by that representation, not a lower bound on the function's complexity.

The distinctions matter:

PHYSICALLY INFEASIBLE UNDER STATED RESOURCE ASSUMPTIONS:
Moving 1 GB of fresh data per token at 10 tokens/s through an effective
2 GB/s SSD channel. Scheduling cannot produce the missing 8 GB/s.
Similarly, 54 billion conventional arithmetic operations per token at
10 tokens/s exceeds a stipulated sustained 100 GOP/s execution engine.

INFEASIBLE ONLY UNDER THE CHOSEN REPRESENTATION:
Keeping the approximately 5.5 GB q4.5 non-MLP matrices resident inside 4 GB.
The function could potentially be represented by a smaller trained network,
shared factors, lower precision, or conditional memory.

RUNTIME LIMITATIONS:
Unbounded mmap residency, full-tensor startup touches, large temporary
dequantized matrices, poorly batched reads, and unfused lookup operations.
These can be changed without proving a new capability result.

PLAUSIBLY CHANGEABLE THROUGH TRAINING:
Backbone width/depth, addressability, precision robustness, output tying,
memory utilization, and the division of work between dense computation
and sparse capacity.

NOT ESTABLISHED:
How much teacher capability survives those interventions, the required
training scale, and exact laptop performance. No architecture-independent
impossibility proof for the overall goal follows from the original file size.

11.4. BROAD SEARCH, WITH SIX SERIOUS ALTERNATIVES

A. Whole-network compression, low-bit training, and parameter sharing

This is the strongest mandatory baseline. Prune or distill the entire
network, including its large attention projections and head, then quantize.
Minitron [S33] shows why post-training recovery must be tested before ranking
pruning choices. QuIP# and AQLM [S36,S37] provide strong low-bit alternatives
to simplistic scalar rounding. Native low-bit training [S38] potentially
moves the compute frontier as well as storage.

But low-bit storage does not automatically eliminate active arithmetic.
Codebook quantization adds decoding or lookup work; binary/ternary kernels
need an appropriate model and instruction-efficient implementation.
DFloat11 [S39] preserves weights losslessly but its roughly 11-bit
representation is far outside this capacity target for 27B.

Low-rank factorization [S35] can reduce both work and bytes. For one original
MLP, replacing each matrix by rank r factors costs approximately
3*r*(5120+17408), versus 267,386,880 original parameters. At r=1024 this
retains about 25.9% of the matrix parameters. That impressive ratio still
leaves the original non-MLP floor unless it too is transformed. There is no
evidence here that the required ranks preserve Qwen3.8 reasoning.

Recursive/shared layers [S34] attack unique weights, but reusing a 1 GB
block eight times can still move about 8 GB through DRAM if the block is
larger than cache. It also executes eight passes and retains separate state
for logical depth. A hypernetwork that regenerates matrices substitutes
generation compute for storage; expanding billions of weights per token
does not solve the CPU limit. Tensor/codebook structure is valuable only
when it supports cheaper computation directly.

Verdict: use compact-model distillation and quantization as the foundation
and control. Keep native low-bit backbones as a serious later option,
especially for 2 GB. Do not gamble on a 27B ternary file being enough.

B. Aggressive contextual sparsity or a new native fine-grained MoE

The old proposal asks how much of the original 17.1B FFN pool can be skipped.
The revised question must include the 9.8B non-MLP matrices and CPU work.
A new narrow-backbone MoE could solve the floor, but then it is already a
substantial architectural transfer problem rather than simple MLP partition.

For the original q4.5 MLP pool, let a be selected fraction and m the
byte-weighted miss fraction of the selected data. Ignoring overfetch,

  SSD bytes/token = 9.626 GB * a * m.

At a=.20 and m=.15, this is 289 MB/token; at a=.10 and m=.05 it is 48 MB.
The latter could be viable, but the approximately 5.5 GB dense resident
floor remains. Low-bit attention, pruning or a new backbone is needed first.

The real competitor is a SMALL native computational backbone plus narrow
experts, trained jointly to use very few active weights. It is credible,
and should be compared if an existing checkpoint fits. Large expert
matrices still make its cold misses more expensive than vector memory.
Existing native-MoE throughput in Sections 1-10 is not a quality comparison
against the exact dense teacher.

Verdict: retain as a competitor, not the first bet. Unmodified dense-group
traces can reject one conversion route; they cannot reject a trained new
representation or discover its ultimate achievable sparsity.

C. Persistent task/segment experts, adapters, or prompt-specific models

Select a small specialist once per request or segment, load it, and reuse
it for tens or hundreds of tokens. Task-level routing has direct prior art
[S42]; compact adapters can further reduce the size of each change.

If a 256 MB specialization bundle is used for 128 tokens, its amortized
traffic is 2 MB/token. At 2 GB/s it costs a minimum 128 ms at selection.
This is a genuine improvement in I/O timescale, independent of token-level
activation persistence. Loading an entire 2 GB specialist costs at least
one second under the same assumption.

The hard issue is composition. A coding request can require parsing,
planning, arithmetic, library knowledge and debugging inside one response.
A task label does not prove that one narrow specialist can reproduce all
those interactions. Frequent switches erase amortization. Choosing weights
after prefill can invalidate the KV/recurrent state produced under the old
weights; a scheme must freeze state-producing weights, train for switching,
or explicitly repay prefix computation.

Verdict: especially attractive for a declared narrow workload or product,
but weaker evidence for broad general capability. Do not freeze routes at
inference and silently assume training would have made them valid.

D. Exact streamed teacher with speculative/block verification

This deserves more attention than the previous notebook gave it. A draft
model can propose a block, and each teacher layer can read its weights once
to verify many positions. This can amortize SSD reads without approximating
the chosen teacher distribution [S40]. Offloading plus speculation already
has system prior art [S41], although its GPU resources differ from ours.

For an illustrative 12 GB of nonresident weights at 2 GB/s, one scan takes
at least 6 seconds. With 32 proposals and independent per-position acceptance
a, expected emitted positions in the standard simplified model are

  E = (1-a^33)/(1-a).

Acceptance       .70     .80     .90     .95     .98
E positions      3.33    5.00    9.69   16.32   24.33
I/O-only tok/s    .56     .83    1.62    2.72    4.05

This is optimistic: all proposal positions are still verified, including
rejected suffixes. Approximately 54 GOP per teacher position and 32
positions require 1.728 TOP per verification block. At 100 GOP/s that is
17.28 seconds of compute, before draft work, state attention and sampling.
Even perfect acceptance does not remove the dense arithmetic per accepted
position. On an accelerator unused during I/O, this trade can be excellent;
a small CPU is a different resource balance.

Acceptance is not truly independent and may collapse precisely on difficult
tokens. Larger trees consume more compute/state. Streaming hybrid recurrent
verification also needs rollback or retained intermediate states. Token
bursts every several seconds do not meet a smooth interactive-latency goal.
An approximate quantized teacher gives exact sampling only relative to that
quantized teacher, not the original BF16 distribution.

Verdict: valuable if teacher fidelity is paramount and latency is relaxed,
or as a quality reference. Not the best main CPU-interactive direction.

E. Small reasoner plus external documents, examples or kNN predictions

Ordinary retrieval provides explicit factual content with far less traffic
than weight streaming. Teacher-generated examples and reasoning distillation
can help. It is a valid baseline, particularly for knowledge-heavy tasks,
not a distraction to be excluded because the original model stored facts
in weights.

However, document retrieval adds query/index work, extra context processing,
and often extra reasoning tokens. A small model may retrieve the right fact
but still fail to use it. Token-level kNN prediction needs a scalable query
index and may improve memorized continuations more than novel computation.
A retrieval corpus containing benchmark answers is not capability transfer.

Verdict: run a controlled retrieval baseline; it may win for practical
applications. Neural memory is attractive because it can inject features
without adding hundreds of textual prompt tokens, but that advantage must
be measured against real RAG rather than presumed.

F. Compact computation plus sparse neural memory

PKM separates a small address mechanism from a large value store [S23].
PEER lets a retrieved item perform a tiny context-dependent computation
[S25]. Memory+ and UltraMemV2 provide stronger-scale evidence for the
family [S26,S27]. This avoids needing the original dense FFN to exhibit
extreme sparsity before training.

There are two materially different access schemes:

  Deterministic input addressing:
    MoLE, STEM, Engram, Memory Grafting [S28-S30,S32].
    Addresses can be known at token entry; cheap to fetch early.
    Risk: limited expressivity when the same local string has different
    meaning or a novel reasoning state needs information absent locally.

  Context addressing:
    PKM/PEER/Memory+/UltraMem [S23-S27].
    A compact query chooses memory using the current hidden state.
    Addresses arrive later, but fetched objects remain small.
    Risk: learning the address space, small random reads and extra barriers.

MoLKV [S31] is an intermediate design: token-triggered loads followed by
contextual selection over a bounded sequence cache. Its limited candidate
set and growing history state need explicit accounting.

Verdict: choose context-addressed memory as the main representation search.
Use deterministic teacher-memory lookup as a simpler comparison and possible
complement if it adds measured value. Do not build a many-component hybrid
before learning which access mechanism actually closes the capability gap.

11.5. PROPOSED REPRESENTATION: A CONCRETE, FALSIFIABLE POINT

The resident backbone

Begin from a strong existing small text model, rather than deleting 85%
of the 27B model and expecting a short repair pass. Qwen3.5-4B is a useful
concrete starting candidate: the primary config has hidden width 2560,
32 hybrid blocks, intermediate width 9216 and tied embeddings [S43].
It is a candidate for controlled tests, not a declaration that it is the
best current small model.

Use Qwen3.8-27B as the teacher and possible initialization/data donor.
Compare a pruned teacher-derived student only if it beats this starting
point after matched adaptation. The teacher remains central to the goal
even when its original runtime graph is discarded.

The memory path

For a concrete candidate, attach a memory branch parallel to the resident
FFN in each of 32 blocks. Let x be the post-attention normalized input:

  z = resident_input_projection(x), dimension 256
  I, alpha = product_key_topk(resident_query(x)), k=32
  delta = resident_output_projection(
              sum over i in I of alpha_i * (a_i dot z) * b_i)
  block output = residual + resident_FFN(x) + gated(delta).

A disk record contains a_i of dimension 256 and b_i of dimension 768.
The sum is formed in the smaller value space before the output projection.
The projections, query, keys, normalization and final residual gate are
resident. The branch is nonlinear through routing/gating; it is not a
single static low-rank approximation. It is also not identical to
UltraMemV2's full routing formulation: this is a simpler PKM-addressed
rank-one candidate inspired by [S23,S25,S27].

Give each bank two sets of 1024 product subkeys of dimension 64. Their
Cartesian product addresses 1,048,576 records. Exact top-32 under the
factorized ADDITIVE key score can be selected from the top-32 subkeys on
each side, using 1024 candidate pairs [S23,S25]. This exactness is about
that restricted score function, not about finding the best arbitrary
teacher feature. Factorized routing may itself limit quality.

Use int8 memory vectors with group scales and fixed 2 KiB records.
The 1024 vector bytes leave space for scale metadata and padding. Align two
records per 4 KiB page so a record never straddles pages. For the conservative
read estimate, every selected record lies in a different cold page.
The row index directly determines file offset: no resident million-key
hash map or ANN graph is required.

This design has:
- Context-dependent coefficients and selected transformations.
- A capable dense fallback path trained together with memory.
- Small persistent address structures.
- An explicit finite read budget independent of total table size.
- No requirement for 80-90% cache hits to meet the byte budget.

At each layer, compute the query and issue the exact requested reads, then
execute the independent resident FFN while reads are in flight. Combine
when both finish. This overlap follows the chosen parallel branch
dependency; it does not require a speculative prediction of future routes.
If reads finish late, the token stalls. Do not silently change model outputs
by dropping required records. Memory dropout during training can improve
robustness, but an optional approximate deadline mode must be evaluated
as a different inference policy.

Why not only four memory layers?

Four sites are a useful cheaper ablation, not an established optimum.
UltraMemV2's layer-count ablation reports downstream gains from distributing
memory more broadly even where validation loss looks similar [S27].
Here 32 sites are affordable in BYTES; latency must decide whether fewer
sites or cross-layer sharing are worthwhile. Coalescing nearby records is
a runtime optimization, not a reason to force semantically unrelated rows
into one large computation expert.

Why this is better positioned than the previous proposal

The earlier scheme preserves a large expensive computation and tries to
avoid loading unused pieces. This scheme first learns a small computation
and then expands capacity with a different storage primitive. The original
9.8B non-MLP floor disappears; the output head is smaller and tied; cold
accesses are kilobytes; and storage need not reproduce the original masks.

Those are structural advantages, not demonstrated quality superiority.
The old scheme may preserve the teacher with less training at a relaxed
RAM budget. The new one carries a much larger learning risk but a much
more plausible <=4 GB physical resource envelope.

11.6. QUANTITATIVE FEASIBILITY AND SENSITIVITY

All estimates in this subsection are derived from declared configurations.
They are not measurements of a trained candidate or a benchmark of the host.
An actual converter must inspect tensor headers and mixed precision.

Resident memory, primary candidate

The dominant matrices of the small reference configuration [S43] give:

  32 * 3 * 2560 * 9216                         = 2.26492416B MLP
  24 * 2560 * (8192+4096+4096+64)               = 1.01056512B linear
   8 * 2560 * (8192+1024+1024+4096)             = 0.29360128B attention
  248320 * 2560, shared embedding/head         = 0.63569920B
  Total dominant matrices                     = 4.20478976B

At 4.5 average bits/weight: 2.3652 GB. The marketed model name is not the
parameter audit; vision and optional MTP are excluded.

Allocation                                           GB decimal
---------------------------------------------------  ----------
Backbone quantized matrices                           2.365
Memory queries/keys/projections/gates, reserved          .150
KV/recurrent/conv state at 4096 tokens, reserved          .150
Chunked prefill and decode scratch                      .180
Bounded memory-record cache                             .128
Runtime, tokenizer, threads, allocation overhead         .200
Allocator/alignment/mixed-precision safety margin        .250
---------------------------------------------------  ----------
Planned charged application memory                     3.423

The state reservation has an arithmetic basis: int8 full-attention KV is
67.1 MB before scales; FP32 recurrent matrices are 50.3 MB before convolution
state. Keeping FP16 KV instead adds about 67 MB. These choices need quality
validation. The .150 GB module allowance accommodates quantized resident
projections and higher-precision keys/query processing; retaining every
projection in FP16 can exceed it.

Do not allocate the disk table as a dense tensor. Do not expand all q4
backbone weights into FP16. A persistent low-bit kernel and bounded scratch
are part of the target representation. Count buffered file-cache residency
inside the budget, or use explicitly bounded read buffers.

A 4 GB physical laptop with 1 GB reserved for OS/other processes has only
3 GB for the application. The above point does NOT satisfy that stricter
case. A roughly 3B backbone with the same style of allowances is about
2.75 GB and is a better initial point there. Conversely, a larger physical
machine with a hard 4 GB application cap can evaluate the 4.2B candidate
fairly if the cap also charges file cache and swap is not hiding overflow.

Stretch point

An approximately 2B backbone at q4.5 consumes 1.125 GB. For illustration,
reserve .100 GB for memory modules, .080 for state, .100 for scratch,
.064 for record cache, .180 for runtime and .150 margin: total 1.799 GB.
That is a <=2 GB APPLICATION design budget, not established quality or a
claim of comfortable desktop operation on 2 GB physical RAM.

A physical 2 GB machine with a 0.7 GB reserve leaves only 1.3 GB. It likely
requires an approximately 1B q4 backbone or a well-trained native low-bit
backbone, reduced context and a lean runtime. BitNet [S38] makes that
direction credible computationally, but does not establish 27B-class
capability. Do not present 2 GB as a trivial quantizer switch on the main
candidate.

Storage capacity and bytes

For 32 banks, 2^20 rows per bank and 2 KiB fixed records:

  disk allocation = 32 * 2^20 * 2048 = 64 GiB.
  useful vector payload = 32 GiB; remaining space is scales/padding.
  rows/token = 32 * 32 = 1024.
  useful vector bytes/token = 1024 * 1024 = 1 MiB.
  record bytes/token = 2 MiB.
  worst distinct 4 KiB page bytes/token = 4 MiB.
  at 10 tokens/s = 40 MiB/s and 10,240 page reads/s.

This includes ZERO cache benefit. It is therefore a more robust byte
envelope than one depending on extreme temporal persistence.
It does not make 1024 small reads free. The relevant bottleneck becomes
request latency/concurrency and CPU dispatch, not sequential SSD bandwidth.

A 64 GiB table is a practical but nontrivial disk commitment, not a required
minimum. One quarter as many rows per bank reduces it to 16 GiB without
changing selected rows/token. Memory capacity should be expanded only when
held-out capability improves; inactive or untrained rows add no value.

Latency sensitivity at k=32, assuming independent reads and QD=8:

  sites     cold pages/token    traffic       100 us/read    300 us/read
      4             128         0.5 MiB           1.6 ms         4.8 ms
     16             512         2.0 MiB           6.4 ms        19.2 ms
     32            1024         4.0 MiB          12.8 ms        38.4 ms

These are sums of ideal per-layer I/O waves before compute overlap.
At QD=1 the 32-site point becomes 102.4 or 307.2 ms. Therefore a synchronous
one-read-at-a-time implementation can fail despite tiny byte volume.
QD=8 requires concurrent requests WITHIN each layer, not eight unrelated
future layers whose hidden-state-dependent addresses are not known.

There is an important adverse sensitivity: the literature's successful
large models can activate far more than 32 memory items [S27].
At 32 sites, k=256 would mean 8192 pages/token, 32 MiB/token and ideal
QD=8 I/O of 102.4-307.2 ms before overlap. At k=768 it becomes 96 MiB/token
and 307.2-921.6 ms under those same service-time assumptions.
If high quality requires those operating points, our initial advantage
shrinks dramatically. Do not borrow large-memory-model quality while
quietly using a much smaller active budget.

Active computation

The backbone has approximately 4.2B large-matrix parameters executed per
token when the tied head is scanned once. The input embedding is just a
row lookup, not a second full embedding matmul. Matrix work is therefore
approximately 8.4 GOP/token, counting a multiply and addition separately.

The 32 memory branches add approximately:
- 10.49M MAC for 2560-to-128 query projections;
- 4.19M MAC for two 1024-by-64 key searches;
- 83.89M MAC for 2560-to-256 and 768-to-2560 projections;
- 1.05M MAC for 1024 selected rank-one vector operations.

Total: about 99.6M MAC or .20 GOP, plus top-k, gates and quantization.
Approximately 8.6 GOP/token is consequently a useful matrix-work budget.
It excludes full-attention score/value work, recurrent updates, softmax,
normalization and memory-management operations. This is not native binary
operation counting or a claim that FP16 FLOPs predict q4 CPU speed.

At the 4096-token context point, QK and attention-value products add about
.537 GOP/token: the reference has 16 actual query heads, not 32. Its doubled
query projection also produces the output gate. Recurrent matrix-vector
work adds at least another .025 GOP, with updates and nonlinear operations
additional. Thus roughly 9.2 GOP is a more complete short-context budget,
while 8.6 GOP denotes the large-matrix-plus-memory calculation above.

The resident keys occupy only
32 * 2 * 1024 * 64 * 2 = 8.39 MB.
The paired 1024-candidate selection per layer is small enough to avoid
querying a disk-resident ANN index. Kernel and sorting overhead still need
measurement; Python callbacks per record are not part of the intended
runtime envelope.

Conservative throughput interpretation

For approximately 2.44 GB/token of scanned quantized backbone plus module
weights, and 8.6 GOP/token, illustrative necessary time bounds are:

  effective DRAM BW   effective compute   max(resource times)
       10 GB/s             40 GOP/s              244 ms
       20 GB/s             80 GOP/s              122 ms
       35 GB/s            150 GOP/s               70 ms

These rates are assumptions spanning weaker to stronger sustained kernels.
The maximum is an optimistic overlap bound; the sum is a more conservative
sensitivity when traffic and work fail to overlap well. Extra state work,
retrieval, dequantization not included in the assumed effective rate, and
synchronization increase observed time. Thus approximately 3-10 tokens/s
is a reasonable envelope to TEST, with >=5 the initial useful-speed gate.
Twenty tokens/s is not supported for this reference point by the model.

The capability frontier could favor a faster 2-3B backbone with more useful
memory, or a larger low-bit backbone with less memory. Optimize the joint
curve rather than insisting that the 4B point must win.

Prefill and time to first token

For 4096 prompt tokens, conventional matrix work is about
4096 * 8.6 GOP = 35.2 TOP before attention/state extras. At hypothetical
sustained prefill rates of .2-1 TOP/s, this is roughly 176-35 seconds.
For 256 prompt tokens, the same optimistic arithmetic is 11-2.2 seconds.
These are sensitivity calculations, not measured x86 prefill rates.

Prompt positions expose more parallel lookup requests and reuse, but they
also execute more model work. Chunked prefill must preserve the RAM bound;
one cannot allocate all memory rows for a long prompt. Warm caches,
conversation state reuse and prefix caching improve repeated interactions,
not the cold-start result. A useful decode rate alone is insufficient if
ordinary prompts take minutes.

11.7. WHAT TRAINING MUST ACCOMPLISH

There is no exact conversion that simply deposits the original weights
into these rows. The representation changes. Learning must determine what
the small backbone can do cheaply and what benefits from sparse external
capacity. Distill the joint system, rather than first distilling all
knowledge into a small model and assuming a later memory attachment will
recover everything else.

A defensible training sequence is:
1. Establish the strongest resident student and teacher baselines. Keep
   the student's tokenizer if compatible; verify token IDs and templates,
   not merely vocabulary size. If tokenizers differ, use sequence-level
   supervision or an explicitly aligned objective.
2. Add memory branches with initially small output gates. Fit addresses,
   projections and memory values on training-only teacher traces while
   allowing a controlled adaptation of the resident backbone.
3. Train on language modeling plus teacher distribution matching and
   verified teacher solutions. Include student-generated prefixes so
   memory is learned on the states encountered during deployment.
4. Introduce the target q4/int8 representation during recovery, preserving
   sensitive state operations at higher precision when justified.
5. Evaluate instruction behavior, calibration and reasoning after the
   representation is trained. A base-model PPL gain does not preserve an
   instruction model's behavior automatically.

A possible objective is:

  L = L_language + lambda_KD * KL(p_teacher || p_student_memory)
      + lambda_budget * measured_or_surrogate_resource_cost
      + optional intermediate-transfer terms.

Hard limits on selected records, record precision and resident dimensions
are preferable to an unconstrained sparsity penalty followed by discovering
that the result misses the budget. A cost term can choose how to distribute
reads among layers, but training cannot violate the hardware envelope.

Intermediate matching requires learned alignment between unequal widths and
depths. An original teacher hidden state is not automatically a meaningful
student residual. Do not require a narrow student to reconstruct every
teacher feature in Euclidean norm; optimize task-relevant behavior and use
intermediate losses as interventions with ablations.

Teacher-derived initialization has several possibilities, none guaranteed:
- Factor/cluster teacher-conditioned residual targets in student coordinates.
- Fit small rank-one local maps within clusters of training states.
- Initialize an input-addressed comparison with frozen teacher n-gram
  representations, following the closest transfer precedent [S30].
- Initialize values conventionally and let end-to-end distillation organize
  them if forcing teacher coordinates proves harmful.

The first two are hypotheses about learning an addressable residual
dictionary, not validated extraction algorithms. Selecting an initialization
must not be mistaken for having transferred capability.

A large table creates a learning-coverage problem. At 1B training tokens and
32 selections per bank, uniform use would give about 30,500 selections per
row of a million-row bank. Actual use is very nonuniform. Measure distinct
updated rows, stale rows, route entropy and quality on infrequent patterns.
Forcefully uniform routing can waste capacity; complete route collapse
can make the SSD bank equivalent to a tiny resident module. Both need tests.

The strongest failure mechanism is representational, not storage:
the teacher's advantage may require context-dependent computation that the
small backbone cannot reproduce. Memory then improves lexical/factual
completion while leaving planning, code synthesis and novel reasoning near
the small-model ceiling. Alternatively, it may take pretraining-scale
optimization to build the necessary division of labor. Neither failure can
be repaired by a better read scheduler.

11.8. CLOSEST PRIOR WORK AND EVIDENCE LIMITS

The following short source records identify what the new evidence actually
supports. Their measurements are not transferred into our laptop estimates.

[S23] Large Memory Layers with Product Keys, Lample et al., NeurIPS 2019.
Two small key codebooks address a much larger value table. This is the
closest foundation for a small resident retrieval index. Exact selection
under the factorized score is not arbitrary semantic nearest-neighbor
retrieval. It is prior art for the address mechanism, not proof of a
4 GB dense-teacher replacement.

[S24] Large Product Key Memory for Pretrained Language Models, Kim and
Jung, Findings of EMNLP 2020.
Studies attaching PKM to pretrained models, including stale memory usage.
Pretrained initialization and adding memory alongside an FFN improve
utilization and performance. This directly limits any novelty claim for
"add external neural memory to a pretrained small model." Its models and
tasks differ from modern autoregressive reasoning.

[S25] Mixture of A Million Experts, He, 2024.
PEER uses product-key retrieval over tiny single-neuron experts and reports
language-model performance/compute improvements. This is close to the
proposed rank-one retrieval primitive. It does not supply an SSD CPU
deployment or a dense Qwen conversion.

[S26] Memory Layers at Scale, Berges et al., 2024 / ICML 2025.
Memory+ combines lookup with context-dependent gating. Experiments scale
memory to 128B parameters, with substantial factual-task gains and
comparisons against dense and sparse baselines. The paper reports
outperforming dense models with more than twice its computation budget.
Its comparison MoE routing and GPU implementation must not be conflated
with every modern MoE or a laptop. It shows useful memory capacity, not
that all reasoning capacity can be externalized.

[S27] UltraMemV2, Huang et al., 2025.
The closest large-scale architectural evidence: compact computation plus
large sparse memory, compressed pre/value spaces, and memory in every
block. Reported configurations include 2.5B activated parameters with
120B sparse parameters at top256 and 60B at top768. More active values
can matter more than a larger table. Training extends to trillions of
tokens; some comparisons improve materially only after continued training.
These are serious warnings against assuming top32 and a short adaptation
run inherit its capability. The authors' public repository exposes model,
memory-layer and training code; it is not evidence of our proposed bounded
x86 SSD runtime.

[S28] Mixture of Lookup Experts, Jie et al., ICML 2025.
Experts consume fixed token embeddings during training, so their outputs
can be precomputed into token-indexed tables for inference. Experiments
cover 160M, 410M and 1B active-model scales. This is direct prior art for
replacing transferred matrices with transferred outputs. It changes the
expert input semantics; an arbitrary contextual dense FFN cannot simply
be tabulated by token ID.

[S29] Conditional Memory via Scalable Lookup (Engram), Cheng et al., 2026.
Combines deterministic n-gram lookup with contextual gating. The
27B-total model improves over an iso-parameter/iso-FLOPs MoE baseline,
including reasoning measures; this is not a 27B dense-model equivalence
claim. Its offload demonstration moves tables to host RAM over PCIe,
reporting less than 3% overhead for a 100B table. The paper discusses
NVMe hierarchy, but that is not our measured SSD result. Exact token-based
addresses and the ability to fetch them early are useful properties.

[S30] Memory Grafting, Cheng et al., May 2026.
Builds frozen conditional memory from pretrained donor hidden states and
retrieves through longest matching n-grams. Its 2.8B-trainable,
0.55B-active recipient, trained on 100B tokens, averages 53.86 versus
51.95 for its MoE baseline and 52.43 for vanilla Engram. A 0.92B setting
uses 50B training tokens. The appendix explicitly lacks a full matched
knowledge-distillation comparison. Thus this is the closest donor-to-memory
precedent, but the modest gain does not establish preservation of most
donor capability or cheap post-training conversion. It is a preprint.

[S31] Mixture of Lookup Key-Value Experts, Wang, December 2025.
Adds context-dependent access over cached token-associated key/value
experts. The shown experiment uses 197M active parameters, with validation
loss 2.9985 versus 3.0180 for gated MoLE. A sliding history bounds the
candidate set. This is relevant prior art for sequence-cache selection,
but small-scale validation loss is weak evidence for general reasoning
retention or hard memory-cap latency. It is a preprint.

[S32] STEM, Sadhukhan et al., January 2026.
Replaces the FFN up-projection with token-indexed embeddings, retaining
contextual gate and down projections. It demonstrates another useful
compute/memory separation. In the original Qwen geometry, replacing only
one of three MLP projections still leaves too much dense computation and
the non-MLP floor; use it on a compact backbone if tested.

[S33-S39] Compression and backbone alternatives.
Minitron [S33] provides whole-network structured pruning plus distillation.
Relaxed Recursive Transformers [S34] provide pretrained layer tying with
depth-specific low-rank adaptations. SVD-LLM [S35] supplies
activation-aware low-rank reconstruction. QuIP# [S36] and AQLM [S37]
improve very-low-bit weight representations.

BitNet b1.58 2B4T [S38] reports 29 ms/token on an i7-13800H with eight
threads, generating 128 tokens using bitnet.cpp. Its headline .4 GB
memory number EXCLUDES embeddings. It was trained on 4T tokens and has
small-model-scale capability; neither its memory number nor its speed
should be assigned to a post-hoc 27B conversion.

DFloat11 [S39] preserves original weights with lossless compression to
approximately 70% of BF16 size. Useful for other capacity regimes, it
cannot reach this RAM target for an intact 27B model.

[S40-S43] Controls and concrete configurations.
Speculative decoding [S40] motivates the exact-output control;
SpecOffload [S41] combines speculation with GPU/CPU offloading.
Task-level MoE [S42] establishes coarse routing as prior art, especially
in translation. Qwen's small-model configuration [S43] supplies the
concrete resident-backbone dimensions used above.

11.9. WHAT COULD ACTUALLY BE NEW

Already established, and NOT new:
- Sparse key/value memory, product keys, and tiny retrieved experts.
- Context gating and dense-plus-memory branches.
- Adding memory to pretrained models.
- Token/n-gram lookup, offline expert outputs and teacher-hidden-state memory.
- Quantized backbones, distillation, SSD caches, prefetch or asynchronous reads.
- The general idea that memory and computation should be separated.

A potentially publishable contribution would be an experimentally validated
way to transfer a strong modern dense teacher into a small CPU-resident
backbone plus an SSD memory representation, with a hard bound on both
resident bytes and dependent cold-read cost. The comparison must show
improvement over matched distillation, low-bit dense models, ordinary
retrieval and suitable small sparse models.

A more specific unvalidated research hypothesis is that jointly learning
the residual representation, factorized addresses, active memory width and
bit precision under a measured latency budget can transfer capability more
efficiently than either teacher-logit distillation alone or frozen lexical
memory. Its success, training efficiency and novelty are not established.

The combination "small student + teacher memory" is too close to [S24,S30]
to claim by itself. Even if the system works, novelty may reside only in
the demonstrated Pareto frontier, training recipe and careful experimental
negative results. The search supports identifying close prior art; it is
not an exhaustive legal or academic novelty certification.

11.10. SINGLE FIRST EXPERIMENT: DOES FINITE MEMORY CLOSE THE GAP?

Run one controlled DISTILLATION-AND-MEMORY experiment before building an
SSD inference engine. Use an existing small pretrained backbone and the
actual Qwen3.8-27B teacher. The principal test is whether a finite, bounded
memory interface transfers useful capability beyond matched small-model
training. Pure activation-mask tracing tests the old representation instead.

This experiment is a prospective model-quality test. Analytical arithmetic
checks in this appendix do not substitute for it. It needs larger training
resources and does not require a working laptop storage implementation.

Pre-register the dataset split, capability suite and budgets

Use a mixed training corpus covering text, code, math, multilingual inputs
and instruction behavior, plus verified teacher demonstrations. Freeze
held-out documents, problem families and evaluation prompts before creating
any memory. Deduplicate train/evaluation material. Evaluate unfamiliar
combinations, entity substitutions and new algorithmic instances, not just
near-duplicate continuations.

Use a 4096 context limit and fixed answer-time/token budgets. For reasoning,
report math exact match, executable code pass@1 and held-out compositional
tests. Include instruction compliance and factual QA, but do not let those
mask failure on reasoning. Measure teacher scores directly under this
protocol; vendor benchmark numbers are not the denominator.

Main arms

  A: strongest resident student, ordinary matched distillation.
  B: same student with the proposed contextual memory, same teacher data
     and optimization budget, evaluated at deployment precision.
  C: the best resource-matched resident-only control, allowed to spend
     B's resident module/cache budget on useful model capacity instead.
  D: token/n-gram-addressed teacher memory as a simpler memory control.

A versus B measures value beyond ordinary distillation. B versus C tests
the actual memory/latency frontier. B versus D tests whether contextual
access earns its complexity. At fixed training tokens, also report actual
training FLOPs; at fixed training FLOPs, allow the simpler controls more
updates. Do not call unequal resources "matched."

Start with a modest table and grow to the declared 64 GiB ceiling only if
the smaller bank is used and helps. Primary inference budget:
32 sites, top32, 2 KiB records, <=4 MiB cold pages/token. Predeclare one
resource-relaxed diagnostic, such as top128, to tell whether the active
budget is strangling quality; this is not a valid result for the original
budget unless its measured CPU latency also passes.

Train all useful backbone parameters or a documented sufficient recovery
subset after a short stabilization phase. A frozen student that cannot
learn to use a new channel is not a fair rejection of the architecture.
Compare a small number of sensible gate/learning-rate choices using
validation data; do not tune on the final tests.

Use 100M tokens as a pilot checkpoint and a predeclared approximately
1B-token cap for the first decision. These are experimental budget choices,
not a claim that 1B tokens suffices. Track learning curves, memory usage
and at least two seeds at the decision point when variance is material.
A still-improving curve at the cap implies budget-limited uncertainty,
not a mathematical impossibility result.

Oracle control to separate addressing from representation

For B, retain a diagnostic mode in which a training-fitted teacher-assisted
selector chooses rows from the SAME finite, frozen bank, subject to the
same row and precision budget. Teacher access at evaluation is permitted
ONLY in this explicitly nondeployable diagnostic. It must never supply
new per-example values, next-token answers or future tokens. Bank contents
come exclusively from the training split.

A strong finite-bank selector can distinguish poor learned addressing from
an inadequate value channel. It is not a true global optimum over all
possible banks, and failing to find good rows is not a proof that none
exist. Fitting a new row to each test prompt would instead be an online
teacher service and invalidates this diagnostic.

The most informative result patterns are:
- B and oracle both fail: little evidence this finite representation closes
  the gap at the chosen backbone and training budget.
- Oracle succeeds but B fails: address learning is the bottleneck; work on
  routing only if a causal cheap selector has a plausible path.
- B succeeds only on familiar strings: memorization/coverage benefit,
  insufficient evidence for the broad goal.
- B improves novel reasoning and survives quantization: proceed to laptop
  storage and kernel validation.

Causal ablations

After training, disable memory, shuffle row-to-value assignments, and
replace cold rows with the trained no-memory policy. Real benefit should
depend on the correctly addressed values. The shuffled test must keep
shapes, norms and read counts comparable. Log held-out route coverage,
active rows, retrieved-byte budgets and layer-specific gains.

Compare PPL and KL as diagnostics; give KL units in nats/token and report
the full-token distribution or the precise approximation used. A percentage
of "local KL" is not a well-defined capability criterion.

Decision criteria

Let Q0 be the best matched resident-only control, QT the teacher, and QM
the memory system on a predeclared aggregate of comparable domain metrics.
For a material positive teacher gap, define gap closure:

  G = (QM - Q0) / (QT - Q0).

Report per-domain G as well; exclude near-zero denominators rather than
letting them dominate.

Proceed to systems work if the deployment-precision, causal-memory arm:
- closes at least 25% of the material teacher gap;
- improves at least two of math, code and novel compositional reasoning,
  with paired confidence intervals supporting the improvement;
- does not incur a material instruction/long-context regression;
- respects the representation budget, and a conservative latency estimate
  remains compatible with >=5 tokens/s.

The 25% gate is evidence of research traction, NOT the final goal.
For example, teacher .80, control .60, memory .65 closes 25% of the gap,
yet retains only 81.25% of raw teacher accuracy. Final success should aim
for approximately >=90% chance-adjusted teacher performance where defined,
with no major domain collapse, under the hardware/time limits.

Abandon this direction as the PRIMARY near-term bet if, after the
predeclared cap and reasonable training stabilization, the upper confidence
bound on gap closure is below 10%, or the gains are confined to familiar
factual completions while math/code/composition show no meaningful gain.
If even the finite-bank oracle fails similarly, stop optimizing retrieval
and storage. If only the oracle works, abandon this particular routing
recipe rather than claiming a usable inference architecture.

Also abandon this operating point if:
- gains disappear at q4/int8 deployment precision;
- closing the gap requires read concurrency, active rows or backbone size
  that fails the latency/RAM limits even with favorable scheduling;
- the memory system is dominated by the resource-matched resident control.

A null result after 1B tokens rejects the practical post-training thesis
at that budget. It does not refute memory networks trained on trillions of
tokens. Extending to that much larger program should be justified by clear
learning curves and an explicit resource decision, not indefinite hope.

Training cost is material

For a 4.2B student, the conventional 6PN estimate at 1B tokens is about
25.2 EFLOP; a dense 27B teacher forward adds roughly 54 EFLOP if evaluated
on every token. Approximately 79 EFLOP excludes attention extras, memory
updates, data work and additional arms. At a sustained aggregate
100 TFLOP/s this alone is about 9.2 days for one such arm. Batched teacher
targets can be reused across arms on identical prefixes; on-policy traces
cannot all be reused. Storing complete 248k-way logits is itself costly.

Frozen donor-memory construction can reduce some teacher cost, but must
not be sold as free. Offline model access, representative data and recovery
compute are necessary resources. Nothing in this notebook authorizes
silently launching a pretraining-scale run.

The full table also has training-state costs far larger than its inference
working set: 32 * 2^20 * 1024 = 34.36B scalar memory values. BF16 values
alone occupy 68.7 GB; FP32 master values and two Adam moments would add
412.3 GB, before gradients, backbone and activations. Sparse, sharded or
offloaded optimization can change residency, but cannot be assumed free.
A pilot with 256-by-256 addresses per bank instead has 2.15B scalar values
and a 4 GiB padded inference table. Start there if necessary, explicitly
label the capacity difference, and account for the larger experiment's
training resources before scaling it. This is another reason to compare
frozen donor-memory and compact dense controls seriously.

11.11. FINAL ANSWERS TO THE TEN DECISION QUESTIONS

1. BEST FRAMING
   Maximize retained capability per unit of resident computation, memory and
   answer latency. Treat the dense checkpoint as a teacher and reusable
   source of learned information, not a mandatory execution graph.

2. BEST DIRECTION
   A strong compact quantized backbone with context-addressed, small-record
   neural memory on SSD, jointly distilled from the teacher. Start with
   product-key retrieval and low-dimensional rank-one memory records;
   compare deterministic teacher-memory lookup and plain distillation.

3. WHY BETTER THAN THE CURRENT PROPOSAL
   It removes the original non-MLP memory/compute floor and reduces the
   cold access unit before optimizing storage. The example meets a byte
   envelope with no cache hits. Quality superiority remains unproven.

4. ROUGH FEASIBILITY
   Primary point: about 3.42 GB charged application RAM, about 8.6 GOP/token
   plus state work, 64 GiB memory-table allocation and 4 MiB worst distinct
   page reads/token. CPU matrix execution and dependent random-read latency
   dominate. Target >=5 tokens/s; approximately 3-10 is a sensitivity
   envelope, not measured performance. Stretch: approximately 1.8 GB with
   a 2B core, with greater quality risk and separate OS accounting.

5. WHAT MUST CHANGE
   Train a smaller state/computation path, usable memory values and
   addresses, their interaction with the dense path, and robustness to
   deployment precision. Teacher hidden coordinates and neuron groups
   cannot simply be copied without learning an interface.

6. CLOSEST PRIOR WORK
   PKM, pretrained-PKM, PEER, Memory+ and UltraMemV2 for the architecture;
   Memory Grafting for donor-to-memory transfer; MoLE/Engram/STEM/MoLKV
   for alternative addressing. Minitron and low-bit models are controls.

7. WHAT MAY BE NEW
   A demonstrated modern dense-teacher transfer and capability/latency
   frontier under a fully charged <=4 GB x86 CPU/SSD budget. The core
   ingredients and generic combination are already close to prior art.

8. STRONGEST FAILURE REASON
   The missing capability is computation that the small backbone cannot
   perform, rather than information that small memory records can supply;
   or learning that separation takes an unaffordable training program.

9. HIGHEST-INFORMATION FIRST EXPERIMENT
   Matched student distillation with and without finite contextual memory,
   an input-addressed control, and a finite-bank teacher-assisted routing
   diagnostic. Measure held-out capability at the intended precision and
   resource budget before building the storage engine.

10. ABANDONMENT RESULT
    Less than 10% credible gap closure after the declared decision budget,
    especially when even the finite-bank diagnostic fails on novel
    reasoning; or domination by a resident-only control after accounting
    for real RAM, CPU latency and extra reasoning tokens.

The defensible conclusion is not that this goal is solved. It is that a
small computation engine with a different learned storage representation
has a better plausible resource frontier than paging fragments of the
original dense network. The research should now try to falsify its
capability-transfer advantage.

12. NATIVE-SPARSE MODEL PIVOT
============================================================

12.1. The problem changes when sparsity is native

The previous sections treated sparsity as something that had to be created
from a dense Qwen3.8-27B teacher. That is no longer the right default. A
native sparse model already contains three valuable properties:

1. Its router has learned which computation is useful for the current hidden
   state.
2. Most expert weights are provably inactive for that token.
3. The model was trained to combine the active experts, rather than asking a
   post-hoc pruning procedure to discover a new computation graph.

The research problem is consequently not "compress a 27B dense function until
it becomes sparse." It is:

    execute a native sparse conditional computation graph on a CPU when its
    non-expert trunk is resident, its routed experts are mostly on SSD, and
    the router is allowed to remain exact.

This distinction matters because the limiting resource is no longer just
resident parameter bytes. It is the product of:

    active CPU work
    + expert bytes that must cross SSD -> RAM per token
    + request and dispatch overhead
    + the resident non-expert floor
    + quality loss if a missing expert is dropped, replaced, or rerouted.

There are four different claims that must not be conflated:

- It is physically impossible to keep all routed pools resident under 4 GB.
- It may be possible to execute exact selected experts from a larger file.
- A current runtime may be unable to bound page faults, request count, or RSS.
- Training may change expert representation, route locality, precision, or
  active K, but it cannot remove the CPU and storage work for free.

The primary direction below therefore starts with exact native routing and
makes approximation a separately measured post-training branch.

12.2. Candidate comparison from the verified configurations

The official configurations are [S44] and [S45]. Both use hidden size 2048
and routed expert intermediate size 512. A routed expert with gate, up, and
down matrices contains:

    3 * 2048 * 512 = 3,145,728 weights.

At four bits, the packed payload is about 1.57 MB. Scales, zero points,
alignment, and tensor headers make a practical contiguous bundle roughly
1.7--1.8 MB in the accounting below. This is an estimate, not a substitute
for measuring the actual GGUF/safetensors bundle. Edge0 reports about 310 MB
per Qwen3.5 layer after its particular quantization and packing, so the
actual file format must be measured before an implementation decision.

+-------------------------------+------------------+------------------+
|                               | Qwen3.5-35B-A3B | Qwen3-Next-80B-A3B|
+-------------------------------+------------------+------------------+
| layers                        | 40               | 48               |
| routed experts/layer          | 256              | 512              |
| native routed K               | 8                | 10               |
| routed expert bundles/token  | 320              | 480              |
| routed pool, rough Q4        | 18 GB            | 43 GB            |
| routed bytes/token, no hit   | 0.48--0.57 GB    | 0.72--0.86 GB    |
| routed expert MACs/token     | 1.01B            | 1.51B            |
| routed+shared expert MACs    | 1.13B            | 1.66B            |
+-------------------------------+------------------+------------------+

The "3B active" labels therefore conceal an important systems difference.
Qwen3-Next has about 1.47 times as much routed expert compute and 1.5 times
as much cold routed traffic in this decode accounting. It may have more
capability per active parameter, but that is not a hardware advantage.

Qwen3.5 is the only candidate with an already demonstrated SSD-resident
deployment in the target family. Edge0 documents Qwen3.5's 40 layers and 256
experts, and its edge0-35b profile uses staged K=4 routing with a prerouter,
LRU/cache, fixed slots, and SSD-backed tensors [S46]. That result is a
valuable baseline, but it is not proof of exact native top-8 execution on
Linux/x86: K=4 changes the active computation and the measured device is an
Apple M4 Pro with MLX. Edge0's reported approximately 2.9 GiB active memory
and 14.9--17.7 decode tok/s should be treated as an Apple/MLX reference,
not an x86 guarantee.

Qwen3-Next is a serious second candidate rather than a discarded model. Its
larger total capacity at similar advertised active size makes it an excellent
capability-density hypothesis. It is, however, the wrong first engineering
target unless a route trace shows that its higher quality compensates for 48
layers, 10 routed experts per layer, 512 expert identities, and substantially
higher request pressure.

12.3. What cannot work without changing the representation

The following are hard negative results, not tuning opportunities:

- Loading either complete routed pool into RAM violates the budget by a wide
  margin: about 18 GB for Qwen3.5 and 43 GB for Qwen3-Next before KV/state.
- Reading every selected Qwen3.5 expert synchronously at 10 tok/s requires
  roughly 5.7 GB/s of fresh payload. Qwen3-Next needs roughly 8.5 GB/s.
  Ordinary consumer SSD paths, especially random/range reads with filesystem
  and queue overhead, cannot promise this.
- At an effective 4 GB/s, the bandwidth-only lower bound is about 142 ms per
  no-hit Qwen3.5 token and 212 ms for Qwen3-Next. CPU compute and first-byte
  latency are additional.
- Native mmap is not a memory budget. Every touched page can contribute to
  RSS/page-cache pressure, and the kernel does not know that a research
  runtime requires a strict expert working set.

The following are representation/runtime limitations, not laws of the model:

- A single contiguous bundle per expert can replace nine small reads
  (weight/scale/bias for each of gate/up/down).
- Layer-major storage, expert-ID reordering, explicit fixed-size buffers, and
  asynchronous pread/io_uring can make the request stream schedulable.
- A bounded global cache can exploit hot experts, but a generic LRU is not
  enough. SpecMD reports that expert access is sequential in layer position
  and that least-stale policies can reduce collision misses [S48].
- A transfer-only predictor can hide reads without changing the native route.
  Edge0's prerouter and recent SpecPrefetch work already establish this
  pattern [S46, S47]. A predictor which silently changes the selected experts
  is a different, approximate model.

12.4. The direction to pursue

The strongest direction is a native-route-preserving, storage-aware MoE
runtime paired with storage-aware post-training. The stages are deliberately
ordered so that model quality is not spent before the physical bottleneck is
measured.

Resident path:

- Keep attention/linear layers, routers, norms, embeddings/output head, and
  the shared expert resident in quantized form.
- Treat the shared expert as a first-class resident path, not as a fallback
  approximation for missing routed experts.
- Reserve an explicit RSS budget for KV/state, staging, and a global routed
  expert cache. Do not depend on an accidental OS page cache.

Routed path:

- Store each routed expert's gate/up/down tensors as one aligned contiguous
  bundle, preferably layer-major.
- Use fixed slots and double buffering. Sort selected IDs before reads and
  coalesce only ranges that are physically adjacent.
- Compare mmap/page faults against explicit pread and io_uring. The latter
  makes queue depth, cancellation, read completion, and eviction measurable.
- Use a cache policy aware of layer position and upcoming work (least-stale,
  next-layer protected), rather than LRU alone.
- Implement a fused CPU kernel that gathers selected IDs, consumes Q4
  weights directly, fuses gate/up where possible, applies the gated
  activation, and accumulates down projections. Hundreds of tiny independent
  GEMMs will otherwise dominate even if SSD bandwidth is sufficient.

Prediction path:

- Train a very small next-layer or pre-attention predictor solely to submit
  asynchronous reads. It must never alter the native router in the exact
  mode.
- Score precision, recall, wasted bytes, synchronous misses, and p95 lead
  time. A 99% prediction recall with 70% precision can be worse than a
  smaller, more precise prefetch set.
- Treat speculative decoding as a later option. SP-MoE shows that drafting
  can create a prefetch window, but it also increases the number of expert
  requests and has GPU/verification assumptions [S49].

The model-side research contribution should be a storage-aware expert
representation, not another generic prefetch paper. The most promising
candidate is a cross-expert shared-basis representation:

    expert_e = resident shared basis + SSD-resident expert coefficients/residual

For example, gate/up/down matrices can be factorized across experts, with
shared basis matrices resident and small per-expert low-rank coefficients or
residuals on SSD. A factorized representation can reduce the cold transfer
unit from approximately 1.7 MB to a few hundred KB at moderate rank. It
also creates a new compute tradeoff: the shared nonlinear SwiGLU path cannot
always be reused by simple linear algebra, so the factorized kernel may do
extra small projections. This must be learned and distilled, not assumed
from an SVD reconstruction error.

This is a research hypothesis, not a novelty claim. SPICE already combines
low-rank expert surrogates with speculative prefetch and CPU residual work
[S50]. Low-rank compression, mixed precision, expert clustering, and
cache-aware routing also have prior art [S48, S51 and the earlier notebook
sources]. The defensible contribution would be a route-exact CPU/SSD format
and a storage-aware fine-tuning objective for Qwen3.5/Qwen3-Next, evaluated
under a hard RSS cap with quality and bytes/token reported together.

The post-training ladder should be:

1. Exact native top-8 Qwen3.5 with ordinary Q4 expert bundles.
2. Exact native top-8 with layout, cache, prefetch, and fused CPU kernels.
3. Per-expert mixed precision selected by contribution and measured against
   all-Q4.
4. Shared-basis/residual experts trained with output/logit distillation and
   a byte/latency penalty.
5. Only then, an adaptive-K or cache-aware router fine-tune that can reduce
   routed K. Any K reduction is an explicit quality trade, not a runtime
   detail.
6. Optional route-locality regularization, constrained by teacher KL and
   load-balance losses. It is useful only if it improves reuse without
   collapsing specialization.

This sequence keeps the previous small-backbone plus SSD neural-memory
proposal in Section 11 as a valid alternative. That branch attacks the
resident floor by changing the model family. The native-sparse branch is
stronger when an existing MoE can retain more high-end capability, but it
cannot honestly promise a 2 GB deployment without more aggressive
factorization or a smaller resident trunk.

12.5. Quantitative budget

A reasonable first Qwen3.5 planning envelope is:

+-----------------------------+------------------+
| component                   | charged RAM      |
+-----------------------------+------------------+
| non-expert trunk and head  | 2.2--2.8 GiB     |
| routers, shared experts,   | 0.15--0.30 GiB   |
| KV/state at 4k context     | 0.10--0.30 GiB   |
| expert cache               | 0.25--0.60 GiB   |
| staging, buffers, runtime  | 0.15--0.30 GiB   |
+-----------------------------+------------------+
| total target               | 2.85--4.30 GiB   |
+-----------------------------+------------------+

The broad range is intentional. Edge0's approximately 2.9 GiB active figure
suggests the lower part is attainable with a carefully bounded runtime, but
a Linux/x86 process, longer context, allocator behavior, and quantization
format can push it beyond 4 GiB. A 64/128/256 expert cache is approximately
113/226/453 MB using the conservative bundle estimate. A strict 2 GiB target
is not credible for an unmodified Qwen3.5 path; it requires a smaller
resident trunk, more aggressive quantization, and/or factorized experts.

For Qwen3-Next, a provisional planning range is 3.1--4.4 GiB. Its exact
linear-attention state and output/runtime accounting must be measured from
the official configuration, not inferred from the marketing active count.
It should not be selected because it has 80B total parameters; it should be
selected only if a capability evaluation justifies its larger I/O and compute
budget.

Active work is approximately 6--10 GFLOP/token for Qwen3.5 once the
non-expert path, router, attention/linear state, dequantization, and output
head are included. Qwen3-Next has about 1.47 times the routed expert MACs,
although its overall advertised active count remains near 3B. A 10 tok/s
target therefore needs roughly 60--100 GFLOP/s of sustained batch-1
effective CPU work, plus hidden I/O and dispatch. On a strong AVX2/AVX-512
laptop, 6--10 tok/s is a realistic initial target and 10--12 tok/s is an
optimistic target after fused kernels and cache/prefetch tuning. On a weak
four-core scalar path, 2--5 tok/s is more plausible. The M4/MLX Edge0 number
must not be extrapolated directly to x86.

The storage target should be expressed as fresh bytes per token, not just
model-file size:

- 500--850 MB/token is the no-cache exact baseline.
- At 10 tok/s, an optimistic 4 GB/s SSD requires at least 29% Qwen3.5 hit
  rate and 53% Qwen3-Next hit rate; slower 2--3 GB/s paths need substantially
  higher hit rates.
- A robust design target is below 100--150 MB fresh/token, with p95 token
  latency below 100 ms. This leaves headroom for filesystem, CPU, and queue
  overhead.
- Such a target is plausible only if routes have strong reuse or if the
  transferred representation is smaller. Previous-token route reuse must be
  measured; uniform-random routing would yield only about 2--3% immediate
  overlap.

12.6. What is already prior art

The following claims are not new by themselves:

- SSD/mmap expert streaming, fixed slots, global caches, and a learned
  prerouter: Edge0 [S46].
- CPU mmap expert paging and route fixation: Swap-MoE (earlier notebook
  sources and [S52]).
- Compact pools with explicit pread: the llama.cpp RFC/PoC (earlier sources).
- io_uring/O_DIRECT-style delta reads and fixed slots: NeuroPrefetcher
  (earlier sources).
- Mixed-precision expert offloading: HOBBIT [S51].
- Learned prefetching and scheduling: Edge0, SpecPrefetch [S47],
  SP-MoE [S49], pre-attention prediction [S53], and SpecMD [S48].
- Low-rank expert surrogates and confidence-aware fallback: SPICE [S50].
- Cache-aware routing, expert substitution, and drop-on-miss policies:
  SpecMD [S48]. SpecMD's Qwen results warn that aggressive drop/substitution
  can cost roughly 25--30% task performance, so they are not acceptable
  defaults for a high-capability target.

The potentially new result is narrower and more credible:

    an apples-to-apples, exact-native Qwen3.5 (then Qwen3-Next) CPU study
    under a measured 4 GiB RSS cap, comparing mmap/page faults with
    pread/io_uring, coactivation-reordered bundles, fused selected-expert
    kernels, and a storage-aware post-training expert representation.

The novelty would be the integrated constraint and the measurements, not a
claim to have invented SSD streaming or expert prediction. If the
shared-basis/residual model survives distillation and improves bytes/token
without unacceptable CPU overhead, that representation is the most
interesting architecture contribution. If it does not, the exact runtime
study still has value and the Section 11 branch remains the fallback.

12.7. First experiment with the highest information gain

Do not begin by training an 80B model or by implementing a full engine. Run
one trace/replay experiment on a provisioned Linux/x86 machine with both
official model checkpoints (or an instrumented equivalent):

1. Execute exact native decode on representative chat, code, reasoning, and
   long-context prompts. Record, for every token and layer, selected IDs,
   router weights, physical tensor offsets, and hidden-state timing.
2. Replay the trace with Qwen3.5 first, then Qwen3-Next if assets permit,
   under:
   - mmap/page faults;
   - contiguous one-bundle pread;
   - io_uring queue depths 1, 8, 32, and 64;
   - global caches of 0, 64, 128, 256, and 512 bundles;
   - previous-token, one-layer oracle, and learned prefetch;
   - original and coactivation-reordered expert layouts.
3. Measure fresh bytes/token, total bytes including overfetch, requests/token,
   read-size distribution, hit rate, prefetch precision/recall, wasted
   bytes, synchronous misses, p50/p95/p99 I/O, CPU cycles/token, and charged
   RSS. Verify byte-identical output in every non-speculative mode.
4. Separately benchmark the selected-expert Q4 kernel with storage disabled.
   This distinguishes a storage failure from a compute/dispatch failure.
5. Only if the exact trace is promising, train a small shared-basis/residual
   representation and compare output KL/NLL, bytes/token, CPU cycles, and
   cache behavior against exact Q4.

The trace should be considered a go/no-go gate:

- Continue if Qwen3.5 can sustain a measured fresh-traffic envelope below
  roughly 100--150 MB/token, charged memory below 3.5 GiB, and fused-kernel
  compute leaves a plausible path to 8--10 tok/s before speculative
  approximation.
- Prefer Qwen3-Next only if its capability gain is large and its trace
  remains inside the same memory/latency envelope after the 1.5x traffic
  penalty.
- Abandon this native-sparse direction if exact Qwen3.5 shows no cache/layout
  regime below roughly 250--300 MB fresh/token, if the resident floor
  already exceeds 3.5 GiB, or if storage-disabled selected-expert CPU
  kernels are below about 5 tok/s. Those results mean that a representation
  change or a smaller model family is required; more prefetch tuning will
  not rescue the target.

12.8. Final decision

1. Base model: start with Qwen3.5-35B-A3B. It has the strongest evidence,
   fewer layers and selected experts, and approximately 1.5x lower cold
   traffic than Qwen3-Next. Keep Qwen3-Next as the capability-density
   challenger in the first trace, not as the first runtime commitment.

2. Architecture/runtime: exact native routing; resident quantized trunk and
   shared expert; SSD routed experts in contiguous layer-major bundles;
   bounded global cache with least-stale/next-layer protection; explicit
   pread/io_uring and fused AVX2/AVX-512 selected-expert kernels; a
   transfer-only learned prefetcher. Then test storage-aware shared-basis
   residual experts as the model-side research branch.

3. Expected RAM: 3.0--3.8 GiB for a carefully bounded Qwen3.5 short-context
   process; 3.2--4.4 GiB provisional for Qwen3-Next. The 2 GiB stretch target
   requires a changed/factorized resident representation and is not a
   baseline promise.

4. Expected active compute: roughly 6--10 GFLOP/token Qwen3.5 end to end,
   including approximately 2.3 GFLOP/token in routed plus shared experts.
   Qwen3-Next has approximately 1.47x the routed expert MACs.

5. Expected SSD traffic: exact cold baseline about 0.5--0.6 GB/token for
   Qwen3.5 and 0.7--0.9 GB/token for Qwen3-Next; the viable target is
   below 100--150 MB fresh/token after cache, layout, prefetch, and/or
   factorization.

6. Realistic x86 speed: initially 6--10 tok/s on a strong AVX laptop;
   10--12 tok/s is an optimistic success case. A weak four-core/scalar
   machine may deliver only 2--5 tok/s.

7. Novelty versus Edge0: not SSD streaming or prefetching. The credible
   novelty is a reproducible exact-native Linux/x86 4 GiB study plus
   storage-aware expert representation/fine-tuning and coactivation-aware
   physical layout, with bytes/token, p95 latency, CPU cycles, and quality
   reported jointly.

8. Training/post-training: first none beyond quantization/runtime adapters;
   then train the transfer-only predictor; next learn mixed-precision or
   shared-basis/residual experts with teacher logit/output distillation,
   load-balance preservation, and an explicit byte/latency penalty; only
   later consider adaptive K or route-locality regularization.

9. Strongest failure reason: native routes may have low reuse exactly when
   difficult reasoning matters, while the resident trunk and hundreds of
   small CPU expert kernels already consume the token budget. If so, SSD
   bandwidth and compute fail simultaneously, and neither a better cache nor
   an approximate predictor can preserve high capability at >10 tok/s.

10. First distinguishing experiment: the exact route-trace/replay plus
    storage-disabled CPU-kernel benchmark described in 12.7. It distinguishes
    model capability from cache/layout/runtime accidents before any expensive
    training. Abandon the path on the explicit traffic, RSS, or compute
    thresholds above.

============================================================
13. NATIVE-SPARSE EXPERIMENTAL RESULTS
============================================================

13.1. Exact Phase 0 control

Qwen3.5-35B-A3B IQ2_XXS exact native top-8 inference was demonstrated on a
4-logical/2-physical-core Kaggle AVX2 Xeon. Resident mmap reached 4.8 tok/s at
10,528.7 MiB peak RSS; a separate 32-token llama-bench arm reached 4.945
tok/s. Routed-expert lazy mmap reached 2.7 tok/s at 5,155.3 MiB. The generated
payload and all 7,360 compared route references were identical. The exact
logical selected payload is 280,494,080 bytes/token. Global-LRU replay gives
177.67, 131.67 and 99.16 MB fresh/token at 512, 1,024 and 2,048 bundles.

13.2. Resident CPU ceiling

A three-repeat 64-token sweep measured 2.329, 3.588, 3.999 and 4.614 tok/s
at one through four threads. Four threads with poll=0 reached 4.716 tok/s;
strict affinity reached 4.691 tok/s. Ordinary thread, polling and affinity
tuning therefore changes the four-thread result by only about 2%. The
resident floor is approximately 212 ms/token. Relative to the 370 ms/token
expert-lazy result, approximately 158 ms/token is added by lazy page-fault
and storage-path stalls. At that measured point, resident CPU/DRAM-kernel
execution is approximately 57% of token time and the added lazy-storage path
approximately 43%. Storage is substantial, but cannot raise throughput above
the below-5-tok/s resident ceiling by itself.

13.3. IQ2_XXS single-token selected-expert kernel test

Source inspection showed that the pinned llama.cpp runtime supports IQ2_XXS
in its IQ panel MUL_MAT_ID path but requires eight activation rows per
individual expert. Exact single-token top-8 decode selects eight distinct
experts, so every selected expert has one row and uses the generic vec-dot
path. A controlled patch made only this threshold runtime-selectable.

The upstream threshold-8 arm reached 5.168 tok/s, a same-binary arm with the
panel explicitly disabled reached 5.196 tok/s, and forcing the existing panel
at one row/expert reached 2.940 tok/s. The forced arm is 43.42% slower than
the same-binary generic control and changes RSS by only 0.21 MiB. Its
generated 24-token payload is byte-identical to the generic control and Phase
0 hash, but the current panel shape duplicates a one-row activation tail into
four lanes and is unsuitable for decode. Lowering the threshold is rejected.

CURRENT BOTTLENECK DECISION:

- The exact resident CPU selected-expert/trunk path is the immediate hard
  throughput ceiling.
- mmap storage/page-fault behavior is a major secondary term and the lazy
  process still exceeds the 4 GiB RAM target.
- The next compute experiment should implement or isolate a true one-row
  IQ2_XXS MUL_MAT_ID kernel with reduced dispatch, not force a batch panel.
- Cache/layout/pread work remains justified after the resident kernel is
  improved or definitively bounded.
- A deeper expert representation change is not yet selected. It becomes
  justified if a purpose-built single-row kernel cannot move the resident
  ceiling materially, or if exact bounded storage cannot meet the fresh-byte
  and RSS envelope after compute is addressed.
